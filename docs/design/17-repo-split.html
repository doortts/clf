받는 곳과 말하는 곳을 가른다

update-pipeline-mockup.html 1절은 릴리즈 저장소를 정하지 못한 채 갈림길 네 개를 남겼다. 이 문서가 그 갈림길을 닫는다. github.com/doortts/clf 는 공개로 돌렸고 자동 업데이트의 배포처로 쓴다. 이슈와 소스 원본과 릴리즈 노트 전문은 사내 GHE oss.navercorp.com/sw-chae/clf 에 둔다.

업데이트 상태 기계와 교체 순서는 14-self-update.html 그대로다. 여기서 정하는 것은 두 저장소의 역할과 링크가 가는 곳, 그리고 그에 맞춰 다시 그린 설정 판의 업데이트 구역이다. 5절 시안이 이 구역의 현재 설계고 14 문서 4절을 대체한다.

1. 원칙 하나

갈라 놓으면 링크마다 어디로 가야 하는지 헷갈리기 쉽다. 그래서 규칙을 문장 하나로 줄인다.

기계가 부르는 주소는 전부 github.com 이고, 사람이 여는 주소는 전부 oss.navercorp.com 이다.

이유는 양쪽의 사정이 정반대라서다. 앱은 GitHub 자격증명을 하나도 갖고 있지 않으니 익명으로 읽히는 공개 저장소만 부를 수 있다. 반대로 이 앱을 쓰는 사람은 전원이 사내 계정이 있으니 이슈를 남기고 노트를 읽는 자리는 GHE 가 자연스럽다. 집에서 VPN 없이 써도 업데이트는 도는 이유가 앞 문장이고 이슈 정리가 사내에서 끝나는 이유가 뒷 문장이다.

github.com/doortts/clf 공개
기계용. 앱이 부른다
  • 태그 v0.5.0 과 자산 clf-v0.5.0.dmg
  • 릴리즈 본문: 사람이 다듬은 노트 (카드 3줄의 출처)

  • 이슈. 이슈 남기기 단추의 목적지
  • 릴리즈 노트 전문과 지난 버전 목록

DMG 를 양쪽에 붙이는 이유는 탈출구다. 자동 설치가 막힌 사람에게 보여줄 직접 받기 는 사람용 링크라 GHE 로 가는데, 그 페이지에 파일이 없으면 거기서 다시 github 으로 건너뛰게 만들어야 한다. 문은 한 번에 열려야 한다.

2. 공개 전환은 끝났다

2026-08-20 에 익명으로 확인한 값이다. 이 설계 전체가 익명 읽기 위에 서 있으므로 여기가 전제의 바닥이다. 

GET api.github.com/repos/doortts/clf
  private: false        익명으로 읽힌다. 앱이 부를 수 있다
  has_issues: false     Issues 탭이 이미 꺼져 있다

GET api.github.com/repos/doortts/clf/releases/latest
  404                   저장소가 아니라 릴리즈가 없다는 뜻이다.
                        위 호출이 200 이므로 읽기 자체는 된다

releases/latest 의 404 를 저장소를 못 읽는 것으로 읽으면 안 된다. 릴리즈가 하나도 없을 때 GitHub 이 주는 답이 이것이다. 앱도 이 둘을 구별해야 한다. 첫 릴리즈가 올라가기 전까지는 모든 사용자가 이 응답을 받으므로, 404 는 오류가 아니라 upToDate 로 떨어뜨린다.

한 번으로 끝난 일은 아니다. 릴리즈마다 태그를 밀고, 태그를 밀면 그 태그가 가리키는 커밋들이 같이 올라간다. 이 방식에서 공개 저장소는 계속 살아 있는 소스 미러다. "소스 공개는 GHE" 라는 말은 개발과 열람의 원본이 GHE 라는 뜻이지 github 쪽에 소스가 없다는 뜻이 아니다.

이제부터는 미는 것마다 공개된다. 커밋 메시지와 설계 문서가 그대로 보인다. 사내 사정이나 비밀값이 담긴 커밋은 밀기 전에 걸러야 하고, 한 번 나간 것은 이력을 다시 써도 이미 본 사람을 어쩌지 못한다. 릴리즈 전 검사에 gitleaks detect 를 한 번 끼워 두면 사람의 기억에 안 맡길 수 있다.

공개 README 는 배포 전용임만 적고 사내 주소는 적지 않는다. 공개 문서에서 사내로 가는 링크는 바깥 사람에게는 죽은 링크고 우리에게는 불필요한 노출이다. 앱 안의 사람용 링크는 이미 GHE 로 가므로 (3절) 공개 README 가 그 길을 안내할 이유가 없다.

앱 안에서 바깥으로 나가는 자리 전부다. 이 표에 없는 바깥 주소는 앱에 없어야 한다.

4. 14 문서에서 달라지는 것

업데이트 상태 기계, 확인 주기, 교체 순서는 그대로다. 바뀌는 것은 링크의 목적지와 그에 딸린 화면 세 가지다.

14 문서이 문서
idle 상태의 릴리즈 노트 단추가 github 릴리즈를 연다 그 단추를 저장소 구역의 릴리즈 페이지 로 내리고 GHE 를 연다
새 버전을 하루에 한 번 확인 체크박스로 확인을 켜고 끈다 체크박스를 없앤다. 확인은 늘 돈다. 끌 것이 없는 이유는 5절에

저장할 값이 autoCheckUpdate 까지 세 개 두 개다. lastUpdateCheck 와 seenReleaseTag. 켜고 끄는 값이 없으니 저장할 것도 없다

5. 화면

설정 판의 알림 구역과 멀티 인스턴스 삭제 사이에 업데이트 와 저장소 두 구역이 이 순서로 들어간다. 아래 여섯 장이 이 구역의 현재 설계다. 단추에 붙은 작은 배지는 목적지를 설명하는 시안 표기고 실제 화면에는 없다.

설정은 아래가 아니라 왼쪽 열로 나간다

두 구역을 더하고 나서 팝오버 하단이 화면 밖으로 나갔다. 계정 카드 셋에 설정 판을 이어 붙이면 900점을 넘는데 메뉴바를 뺀 높이가 945점이다. 계정이 하나만 늘거나 업데이트 카드가 펼쳐지면 바닥이 잘린다. 아래로 자라는 구조 자체가 한계였다.

그래서 설정을 열 하나로 떼어 왼쪽에 붙인다. 높이가 두 열 중 더 긴 쪽으로 정해지므로 설정을 펼쳐도 창이 그만큼만 자란다.

실측값이다. 창 좌표를 재 보면 닫힌 상태가 1163..1503 (폭 340, 높이 434) 이고 펼친 상태가 597..1278 (폭 681, 높이 570) 이다.

펼치면 팝오버 전체가 왼쪽으로 밀린다. 위 좌표에서 보이듯 225점을 움직인다. 시스템은 상태 항목 왼쪽 끝에 창을 맞추다가 그 폭이 화면 오른쪽을 넘기면 오른쪽 끝에 맞추는 쪽으로 뒤집고, 그 판단은 우리가 정하는 값이 아니다. 아래로 자라던 구조에서는 없던 움직임이라 적어 둔다.

그래도 왼쪽이 맞다. 어느 쪽에 두든 창은 같은 자리로 밀리니 우리가 정할 수 있는 것은 두 열의 차례뿐이다. 설정을 왼쪽에 두면 본문 열의 오른쪽 끝이 상태 항목 오른쪽 끝과 맞아서 눈이 가 있던 자리 바로 아래에 남는다. 오른쪽에 뒀다면 본문이 상태 항목에서 566점 떨어진 곳으로 간다.

두 열의 제목 줄은 같은 높이에 선다. 설정 열에도 설정 이라고 한 줄 적는다. 열이 갑자기 왼쪽에 나타나는데 이름이 없으면 무엇이 열린 것인지 한 박자 늦게 읽힌다. 그리고 짧은 쪽 열의 조작 줄은 바닥에 붙인다. 허공에 뜬 채 그 아래가 비면 창이 잘린 것처럼 보인다. 설정을 닫으면 열이 하나뿐이라 늘어날 자리가 없고, 카드와 조작 줄 사이 여백은 그대로 16 이다.

아래 여섯 장은 그 왼쪽 열의 업데이트 구역을 상태별로 떼어 그린 것이다.

확인을 켜고 끄는 체크박스는 두지 않는다

끌 것이 없다. 확인은 릴리즈 API 를 한 번 읽는 것이 전부고 아무것도 바꾸지 않는다. 새 버전을 받고 갈아 끼우는 일은 사람이 설치하고 다시 시작 을 눌러야 시작한다. 스위치가 값을 가지려면 켜져 있는 동안 뭔가가 벌어져야 하는데 여기서 벌어지는 것은 톱니에 점 하나가 붙는 것뿐이다.

  • 아끼는 것이 없다. 하루 한 번 익명 호출 하나는 이 앱의 평소 통신량 옆에서 재지지 않는다. 사용량은 몇 분마다 읽는다
  • 꺼 두면 잊는다. 한번 끈 사람은 다시 켜러 오지 않는다. 새 버전을 영영 못 보는 상태를 사용자가 스스로 만들 수 있게 두는 것은 자동 업데이트를 만드는 이유와 반대다
  • 상태가 하나 줄어든다. 체크가 꺼진 동안의 화면과 그때도 점을 띄우는지, 손으로 누른 확인은 어떻게 되는지를 각각 정하지 않아도 된다. 저장할 값도 autoCheckUpdate 하나가 사라진다

대신 지금 확인 이 남는다. 24시간을 기다리지 않고 지금 보는 길은 있어야 하고, 확인을 사용자가 통제하는 방법은 그 한 번으로 충분하다.

지금 확인은 제목 옆 새로고침 아이콘이다

글자 단추로 한 줄을 차지할 일이 아니다. 팝오버 머리에 이미 사용량 지금 새로고침 이 arrow.clockwise 아이콘으로 있다. 같은 뜻을 두 곳에서 다른 모양으로 그릴 이유가 없어서 같은 글리프를 쓴다.

  • 돌리지 않는다. 아이콘이 되면 회전시키고 싶어지는데, 팝오버 머리의 새로고침도 안 돈다. 확인은 대개 1초 안에 끝나고 그동안 도는 그림은 그 자체로 소리다. checking 동안에는 흐리게 하고 못 누르게 하는 것으로 끝낸다
  • 결과 줄의 들여쓰기가 없어진다. 14 문서 시안은 체크박스 글자에 맞춰 20 을 밀어 뒀는데 맞출 대상이 사라졌다. 제목 아래 그대로 붙인다
  • 이름을 붙인다. 그림에는 읽을 글자가 없다. accessibilityLabel 은 "지금 업데이트 확인" 이고 툴팁은 hoverTip 으로 "지금 확인" 이다

접힌 상태의 높이는 제목 줄과 결과 줄, 두 줄이다. 상태가 바뀌어도 이 둘은 자리를 지키고 늘어나는 것은 그 아래 카드뿐이다.

이슈와 릴리즈 노트는 사내 저장소에 있습니다. 사내망에서 열립니다

다시 시도 는 남는다. 확인 아이콘과 하는 일이 달라서다. 아이콘은 릴리즈를 다시 읽고, 이 단추는 막힌 그 단계부터 다시 간다. 직접 받기 가 여는 곳은 GHE 릴리즈 페이지다. 사내 프록시가 github 내려받기를 막아 실패한 경우에도 GHE 에 붙은 DMG 로 빠져나갈 수 있다. 바로 아래 이슈 남기기 가 있어서 막힌 사람이 신고할 문도 같은 화면에 있다

저장소 구역은 상태와 무관하다. 위에서 세 장에만 그린 것은 자리를 아끼려는 것이고 실제로는 여섯 상태 모두에서 같은 모양으로 아래에 있다.

6. 릴리즈 절차. 내보내는 곳이 둘이 된다

scripts/release.sh 의 빌드, 서명, 공증, 자기 검증은 그대로다. 바뀌는 것은 준비물과 마지막 내보내기 구간이다. 

만드는 쪽 (release.sh --publish)

1. 노트 파일 확인. 없으면 초안을 만들고 멈춘다
   git log --format='- %s' v0.4.0..v0.5.0 > .build/notes-v0.5.0.md
   "노트를 다듬은 뒤 다시 실행" 안내 후 exit
        |
2. GHE 먼저.
   git push origin main v0.5.0
   gh release create v0.5.0 clf-v0.5.0.dmg \
      --repo oss.navercorp.com/sw-chae/clf \
      --title "clf v0.5.0" --notes-file .build/notes-v0.5.0.md
        |
3. 공개 쪽은 그다음.
   git push gh main v0.5.0
   gh release create v0.5.0 clf-v0.5.0.dmg \
      --repo github.com/doortts/clf \
      --title "clf v0.5.0" --notes-file .build/notes-v0.5.0.md
  • 노트는 손으로 쓴다. --generate-notes 를 버리는 이유는 둘이다. 공개 쪽에 자동 생성 노트를 쓰면 GHE 이슈 번호 같은 죽은 참조가 들어가고, 그 본문 앞 3줄이 그대로 사용자 카드에 뜬다. 카드에 뜰 글이면 사람이 한 번 읽고 내보내야 한다. 커밋 제목 초안에서 출발하니 쓰는 수고는 다듬기 정도다
  • GHE 가 먼저다. 공개 릴리즈가 생기는 순간부터 앱들이 새 버전을 보고 릴리즈 노트 를 누르기 시작한다. 그 링크의 목적지인 GHE 페이지가 먼저 서 있어야 한다
  • 다시 돌려도 안전하게. 2와 3 사이에서 끊기면 같은 명령을 다시 돌리는 것이 복구다. push 는 원래 멱등이고, 릴리즈 생성은 gh release view 로 있는지 먼저 봐서 있으면 건너뛴다
  • 준비물이 하나 는다. 이 기계의 gh 는 GHE 에만 로그인되어 있다. gh auth login --hostname github.com 을 준비물 목록에 더하고 스크립트 앞머리의 사전 검사에서 두 호스트의 인증을 다 본다. 빌드와 공증이 끝난 뒤에 인증에서 걸리면 아깝다

7. 앱 코드. 주소는 한 곳에만 산다

링크 지도 (3절) 를 코드로 옮긴 것이 이 타입 하나다. 순수 값이라 ClfDesktop 에 두고, 화면과 UpdateModel 은 여기서만 주소를 가져다 쓴다. 저장소를 옮기는 날 고칠 곳이 이 파일 하나가 되게 하는 장치다. 

Sources/ClfDesktop/ProjectLinks.swift

enum ProjectLinks {
    // 기계용. 익명으로 읽히는 공개 저장소
    static let updateRepo = "doortts/clf"
    static var latestReleaseAPI: URL   // api.github.com/repos/.../releases/latest

    // 사람용. 사내 GHE
    static let home = URL(string: "https://oss.navercorp.com/sw-chae/clf")!
    static var newIssue: URL           // .../issues/new
    static var releases: URL           // .../releases
    static func releasePage(tag: String) -> URL   // .../releases/tag/v0.5.0
}

테스트는 ProjectLinksTests.swift 로 조립 결과 URL 문자열을 그대로 잠근다. 조립 실수는 눌러 보기 전에는 안 보이는데 눌러 보는 사람은 대개 사용자다. 저장소 구역의 화면 코드는 Views.swift 의 SettingsPane 에 한 덩이로 들어가고, 열기는 NSWorkspace.shared.open 이다.

8. 위험과 대비

위험왜 생기나대비
안 나갈 것이 다음 릴리즈에 실려 나간다 공개 저장소는 살아 있는 소스 미러다. 태그를 밀면 그 커밋들이 같이 올라간다. 이력이 비공개 전제로 쌓였다는 사실은 그대로다 릴리즈 전 검사에 비밀 스캔을 끼운다 (2절). 사람의 기억에 맡기면 바쁜 날에 새어 나간다. 한 번 나간 것은 되돌릴 수 없다
공개 저장소가 다시 비공개가 되거나 이름이 바뀐다 저장소 설정은 앱 배포와 무관하게 바뀔 수 있다 확인 호출이 404 를 만나면 조용히 지나가고 설정에만 이유를 적는다. 14 문서의 실패 처리 그대로다. 기존에 나간 앱은 영영 새 버전을 못 보므로, 옮길 일이 생기면 옛 주소에 마지막 릴리즈를 하나 남겨 갈아타게 한다
두 릴리즈 중 한쪽만 올라간다 내보내기가 두 번이라 사이에서 끊길 수 있다 순서를 GHE 먼저로 고정하고 (6절) 재실행을 복구 수단으로 삼는다. GHE 에만 올라간 동안은 아무도 다치지 않는다. 앱이 아직 새 버전을 모르기 때문이다. 반대 순서였다면 죽은 링크가 먼저 나간다
이슈가 두 곳으로 갈라진다 공개 저장소에도 Issues 탭이 있다 공개 쪽 Issues 를 끈다. 앱의 이슈 남기기 는 GHE 만 연다
사내망 밖에서 사람 링크가 죽는다 GHE 는 사내에서만 열린다 업데이트 자체는 공개 쪽이라 돈다. 저장소 구역의 힌트 한 줄로 예고하고 그 이상은 하지 않는다 (3절)
노트 없이 릴리즈가 나간다 급할 때 노트 쓰기를 건너뛰고 싶어진다 release.sh 가 노트 파일이 없으면 초안을 만들고 멈춘다 (6절). 빈 본문이면 카드 3줄 자리도 비어서 사용자가 무엇이 바뀌었는지 모른 채 설치 단추만 보게 된다

9. 단계

  1. 공개 전환. 끝남 private: false, Issues 탭 꺼짐까지 확인했다 (2절). 공개 README 정리만 남았고 그건 급하지 않다
  2. release.sh 두 곳 내보내기. github.com 인증 추가, 노트 파일 절차, GHE 릴리즈 생성, 사전 검사. 여기까지 하면 첫 태그 v0.1.0 을 양쪽에 올릴 수 있다. 14 문서 10절의 1단계와 합쳐서 진행한다. notarytool 키체인 프로필 재등록이 이 단계의 첫 일이다
  3. ProjectLinks.swift 와 저장소 구역. 업데이트 기능 없이도 이슈 남기기 와 릴리즈 페이지 는 바로 쓸모가 있다. 테스트 포함
  4. 업데이트 본체. 14 문서 10절의 2 - 4단계 그대로. 링크 목적지와 업데이트 구역 화면은 이 문서를 따른다. 404 를 upToDate 로 떨어뜨리는 것을 UpdateCheck 테스트에 넣는다. 첫 릴리즈 전까지는 모든 사용자가 그 응답을 받는다
