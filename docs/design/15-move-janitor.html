옮긴 자리 청소

옮기기가 지운 레코드를 앱이 되살린다. 의도를 장부에 적어 두고 되살아나면 다시 지운다. 14 세션 공유 의 다음 이야기다.

1. 문제

옮기기 자체는 잘 동작한다. 넣고 지운다. 그 뒤에 옛 계정의 앱 창이 메모리에 쥔 세션 목록을 디스크에 다시 쓰면서 지운 레코드를 되살린다. 사용자 눈에는 "옮겼는데 양쪽에 있다" 로 보이고, 옮기기가 고장 난 것으로 읽힌다.

2. 왜 옮기기를 없애지 않나

공유만 남기자는 안도 검토했다. 잃는 것이 더 많다.

잃는 것왜 문제인가
한 계정만 가리킨다는 안전 기본값 공유는 "동시에 안 쓴다" 는 규율이 전제다. 옮기기는 그 규율이 필요 없다
목록 정리 옮기는 이유의 절반은 옛 계정 목록에서 치우는 것이다. 공유는 영원히 양쪽에 남는다
의도 구분 전부 공유가 되면 겹침 경고가 뜻을 잃는다. 진짜 사고를 골라낼 기준이 사라진다

그리고 공유도 같은 되살림을 당한다. 공유 끊기가 지운 레코드도 앱이 되살린다. 옮기기를 없애도 문제는 안 없어진다. 지우는 동작이 있는 한 청소부가 필요하다.

3. 설계 한 줄

옮길 때 무엇을 어디서 지웠고 그때 활동 시각이 몇이었는지 장부에 적는다. 옛 자리에 레코드가 다시 생기면, 그 계정의 창이 닫힌 뒤에 활동 시각을 워터마크와 비교해서 그대로면 되살아난 것이니 다시 지우고, 더 최신이면 사용자가 진짜 이어간 것이니 항목을 빼고 물러난다.

shared-sessions.json 과 같은 수법이다. 디스크만 보면 의도를 모르니 의도를 따로 적는다. 지우는 쪽이 아니라 지운 것을 지켜보는 쪽을 고친다.

창이 떠 있는 동안은 아무것도 안 지운다. 목록은 앱 메모리에 있어서 디스크를 지워 봐야 화면의 줄은 안 사라지고, 앱이 다시 쓰면 우리가 또 지우는 줄다리기만 남는다. 앱이 언제 어떤 단위로 쓰는지 모르는 채로 그 사이에 끼는 것이 이 설계에서 가장 예측 불가능한 자리였고, 그래서 뺐다. 창이 없으면 되살릴 프로세스가 없으니 한 번 지우면 끝난다. 14 문서 동기화의 "창이 떠 있는 계정에만 쓴다" 와 정확히 대칭이다. 쓰기는 볼 사람이 있을 때만, 지우기는 쥔 사람이 없을 때만.

4. 앱은 삭제를 무덤 파일로 남긴다

계정 폴더에서 실측으로 찾았다. 앱에서 세션을 삭제하면 레코드 local_<sessionId>.json 이 사라지고 그 자리에 deleted_<cliSessionId> 파일이 생긴다. 내용은 삭제 시각 하나다. 

2a063dae-.../ (계정 폴더)
  local_646ff4d7-....json          살아 있는 레코드
  deleted_78133fb6-...             무덤. 내용은 "1785697922353" 뿐

무덤이 가리키던 트랜스크립트는 삭제 뒤에도 남아 있었다. 삭제 순간 앱은 돌던 백그라운드 작업만 죽이고 대화 파일은 안 지웠다. 이 관측이 맞다면 두 가지가 따라온다.

  • 앱의 삭제는 레코드만 지우는 안전한 동작이다. 겹친 상태에서 한쪽 창의 메뉴로 지워도 반대쪽 대화는 안 죽는다 (9절 실험으로 확정한다)
  • 앱이 무덤으로 삭제를 기억한다면, 우리도 지울 때 무덤을 같이 쓰면 앱이 메모리의 목록을 디스크로 되쓸 때 그 세션을 지운 것으로 알아보고 되살리지 않을 가능성이 있다. 되살림 자체가 사라지면 청소부가 할 일이 없어진다

둘 다 관측 하나에 기댄 추론이다. 확정은 9절의 실험이 한다. 무덤 쓰기가 되살림을 막는 것으로 확인되면 move() 가 무덤을 남기는 것으로 설계가 한 단계 더 줄어든다.

6. 장부

~/Library/Application Support/clf/moved-sessions.json. HandoffGrace, SharedSessions 와 같은 자리, 같은 방식이다. 

{
  "cb99a8ae-...": {
    "from": "2a063dae-...",        옛 계정. 여기서 지웠다
    "watermark": 1786288336445,    지울 때 레코드의 lastActivityAt
    "cleaned": 0                   다시 지운 횟수. 안전핀이 센다
  }

항목이 빠지는 조건. 하나라도 맞으면 그 대화는 더 안 본다.

조건이유
옛 자리에 더 최신 활동이 나타남 사용자가 진짜 거기서 이어갔다. 지우면 데이터 손실이다. 겹침 경고에 맡긴다
같은 대화를 다시 옮기거나 공유함 새 의도가 옛 의도를 덮는다. move() 와 share() 가 시작할 때 지운다
받은 쪽 레코드가 사라짐 옮김 자체가 무효가 됐다. 지킬 것이 없다
cleaned 가 3을 넘음 안전핀. 수동 복원을 우리가 계속 먹고 있다는 뜻일 수 있다. 포기한다

나이로는 안 지운다. 되살림이 22시간 뒤에도 왔으니 나이로 자르면 구멍이 다시 열린다. 위 조건이 안 걸리는 항목은 남지만, 10절의 mtime 게이트 덕에 남아 있는 비용이 0 에 가깝다.

8. 우려와 대책

이 설계를 검토하며 나온 우려들이고 각각 어디서 막는지다.

우려방향대책
공유 사본을 시체로 오판해 지운다데이터 손실 공유 장부 확인이 판정의 첫 문이다. share() 와 move() 는 시작할 때 상대 장부의 항목을 지운다. 테스트로 잠근다
사용자가 수동으로 복원한 레코드를 먹는다데이터 손실 cleaned 안전핀. 3번 넘게 되살아나면 의도로 보고 포기한다
앱이 살아 있는 동안 쓰고 지우기를 반복한다예측 불가 창이 없을 때만 지운다. 줄다리기가 구조적으로 안 생긴다. 3절
앱이 작업 없이 act 를 올려 쓰면 청소가 멈춘다기능 무력화 fail-open 으로 둔다. 실측 셋 다 옛 시각 그대로였다. doctor 에 장부 상태를 노출해 관찰 가능하게 한다
장부가 안 줄어든다성능 10절의 폴더 mtime 게이트. 안 걸린 항목의 유지 비용이 0 에 가깝다
창이 떠 있는 동안 겹침 경고가 남는다UX 장부의 대화는 겹침 판정에서 뺀다. 창을 닫으면 청소가 마저 정리한다

9. 실험

4절의 추론 둘을 버리는 세션으로 확정한다. 진짜 대화로는 하지 않는다.

실험 A. 앱의 delete 는 무엇을 지우나

  1. 버리는 트랜스크립트 하나와 그것을 가리키는 레코드를 두 계정 폴더에 만든다. 겹친 상태의 재현이다. 여기까지는 clf 쪽에서 준비한다
  2. 한쪽 계정 창을 다시 띄워 목록에 뜨는 것을 확인한다
  3. 그 창의 세션 메뉴에서 Delete 를 누른다. 사용자 손이 필요한 유일한 단계다
  4. 디스크를 확인한다. 그 계정 레코드가 사라졌나, deleted_ 무덤이 생겼나, 트랜스크립트가 남았나, 반대쪽 계정 레코드가 무사한가

실험 B. 무덤이 되살림을 막나

  1. 실험 A 의 삭제가 끝난 창을 그대로 쓰다가 닫는다. 앱이 종료하며 메모리의 목록을 디스크로 되쓰는 순간이다
  2. 닫힌 뒤 디스크를 확인한다. 지운 레코드가 되살아났으면 무덤은 장식이고 청소부가 필요하다. 안 되살아났으면 move() 가 무덤을 남기는 것으로 되살림 자체를 막을 수 있다
결과설계가 이렇게 된다
delete 가 레코드만 지운다 문구에 "옛 창에서 직접 삭제해도 됩니다" 를 더한다. 사용자가 스스로 정리할 길이 생긴다
delete 가 트랜스크립트까지 지운다 겹친 상태에서 앱 delete 는 금지라고 경고문에 적는다. 청소부의 값이 올라간다
무덤이 되살림을 막는다 move() 와 청소가 무덤을 같이 쓴다. 되살림이 사라져 청소부는 과거 찌꺼기 정리용으로 축소된다
무덤이 안 막는다 7절 판정 그대로 간다

10. 비용

5초마다 장부의 대화 수만큼 일하면 안 된다. 옛 계정 폴더의 mtime 을 먼저 본다. 레코드가 되살아나면 폴더에 파일이 생기므로 mtime 이 반드시 움직인다. 안 움직였으면 그 바퀴는 파일 하나 안 연다. 

sweepMoved():
  for 옛 계정 in 장부가 가리키는 계정들:           // 보통 1-2개
    if 그 계정 창이 떠 있음: continue              // scanInstances 가 이미 안다
    if 폴더 mtime 그대로: continue                 // stat 한 번. 대부분 여기서 끝
    폴더 안 레코드를 읽어 장부의 대화와 대조       // 되살아났을 때만

같은 루프가 이미 프로세스 목록 전수 스캔(scanInstances)을 돌고 있다. stat 한두 번은 그 옆에서 안 보인다.

11. 문구

청소부가 생겨도 옛 창의 화면 목록에는 줄이 남는다. 우리가 지우는 것은 디스크지 앱 메모리가 아니다. 문구가 과장하면 안 된다.

마지막 문장이 6절의 "더 최신이면 물러난다" 규칙을 사용자 말로 옮긴 것이다. 규칙을 숨기지 않아야 물러났을 때 놀라지 않는다. 실험 A 가 delete 의 안전을 확정하면 "옛 창 목록에서 그 세션을 직접 삭제하셔도 됩니다. 대화 본문은 남습니다" 를 한 줄 더한다.

12. 단계

  1. 9절 실험. 앱 delete 의 의미와 무덤의 효과를 확정한다. 결과가 아래 단계의 모양을 정한다
  2. MovedSessions 장부. 적기, 빼기, cleaned 세기, 파일 왕복. TDD
  3. MoveJanitor.plan 판정. 파일 안 건드리는 순수 함수. 7절 흐름도 그대로. TDD
  4. MoveJanitor.run 청소. 실제 삭제와 장부 갱신. move()/share() 의 항목 정리. 실험이 무덤 효과를 확인하면 move() 와 청소가 무덤도 쓴다. TDD
  5. 5초 루프 연결, 창 게이트와 mtime 게이트, 겹침 판정 제외, 문구 교체

안 하는 것이유
