왜 만드나

비슷한 앱이 이미 있다. 그래도 만드는 이유가 셋이고, 그 셋이 이 앱의 범위를 정한다.

다루는 것과 다루지 않는 것

한도 관리 한 가지에 집중한다. 지금 얼마나 남았는지, 어디로 넘어가야 하는지, 언제 넘어가야 하는지. 그 밖은 넣지 않는다.

시스템 경계

대화를 소유하지 않는다

Messages API 는 상태를 서버에 두지 않는다. 전체 대화 이력이 매 요청 본문에 통째로 실려 오므로, 조직을 바꾼다는 것은 같은 바이트를 다른 인증 헤더로 다시 보내는 것이 전부다. 넘겨야 할 세션 같은 것은 없다.

다만 공짜는 아니다. 프롬프트 캐시는 조직 단위라서 전환하면 컨텍스트 전체가 다시 캐시 생성 비용으로 청구된다. 선제 전환을 대화 시작 시점에만 적용하는 이유다.

앱을 꺼도 안전하다

정상 종료할 때 settings.json 에서 clfl 이 심은 줄을 지운다. 앱이 없으면 Claude Code 는 원래대로 직접 호출로 돌아간다. 죽은 포트를 가리킨 채 남겨두지 않는다.

기능

터미널에서 하던 여섯 개 명령과 환경변수 설정이 창 하나로 들어온다.

모델별 쿨다운
한 모델의 주간 한도가 소진돼도 같은 조직의 다른 모델은 계속 쓴다.

가장 빡빡한 창이 임계값 아래면 후순위로 민다. 제외가 아니라 강등이라 가용 조직이 0이 되지 않는다.

빼둘 조직 지정
자동 전환 대상에서 뺀다. 자격증명은 그대로 남고 순서 자리도 지킨다.

반응형에 쿨다운을 걸면 안 된다. 429 는 우리 판단이 아니라 그 조직을 지금 쓸 수 없다는 서버의 통보다. 쿨다운 때문에 넘어가지 못하면 요청이 그냥 실패한다. 선제 전환은 반대다. 우리 판단이라 틀릴 수 있고, 틀렸을 때 왕복하면 캐시를 반복해서 버린다.

어느 창이 조직을 묶는가

5시간, 주간, 그리고 요청한 모델의 주간 중 먼저 바닥나는 쪽이 그 조직을 묶는다. 잔여 기준이므로 최솟값을 본다. 하나만 보면 나머지가 먼저 차는 경우를 놓친다.

모델별 주간이 먼저 바닥난 경우

제외가 아니라 강등이다

임계값 아래인 조직을 후보에서 빼지 않고 뒤로 민다. 전 조직이 임계값을 넘었을 때 쓸 수 있는 곳이 0이 되면 안 되기 때문이다.

tier조건동작
0묶는 잔여가 25% 이상 (임계값 15 + hysteresis 10)선호. 우선순위 순서대로
1그 외. 읽기가 없는 조직도 여기tier 0 이 비었을 때만

hysteresis 가 없으면 임계값 바로 위아래에 있는 두 조직이 대화마다 자리를 바꾼다. 전환은 프롬프트 캐시를 버리는 행위라 왕복 자체가 손해다.

묵은 값을 믿지 않는다

잔여량은 응답 헤더에 편승해 갱신되므로, 오래 쓰지 않은 조직의 값은 며칠 묵는다. 그 사이 창이 리셋됐으면 실제로는 비어 있는 조직을 소진된 것으로 보고 건너뛴다.

그래서 리셋 시각이 지난 창의 읽기는 버린다. 리셋 시각 자체를 모를 때는 판단 방향에 따라 다르게 다룬다. 지금 쓰는 조직을 내보내는 판단에는 쓰지 않고, 후보를 뒤로 미는 판단에는 쓴다. 전자는 틀리면 멀쩡한 조직을 쫓아내고, 후자는 틀려도 그 후보가 조금 늦게 선택될 뿐이다.

폴링하지 않는다

5시간과 주간은 응답 헤더로 공짜로 들어온다. 모델별 주간만 Usage API 가 필요한데, 타이머 대신 캡처 직후, 갱신 직후, 팝오버 열림, 선제 판단, 후보 검증 다섯 계기에만 부른다. 사용량을 물어보다 사용량을 소진하면 앞뒤가 맞지 않는다.

메뉴바

기본은 사용 중인 조직의 세 창을 막대로 보여주는 것이다. 메뉴바 폭이 아까우면 좁은 모드로 바꿀 수 있다.

조직 이름 대신 두 글자 코드를 쓴다

메뉴바는 폭이 귀하다. 조직 이름을 그대로 쓰면 시계와 다른 메뉴 항목을 밀어낸다. 메뉴바에서만 축약 코드를 쓰고, 팝오버와 설정 창은 원래 이름을 그대로 쓴다.

조직 이름코드규칙

team2T2알파벳순 2번째

표시 모드는 하나만 고른다

폭과 정보량은 맞바꿀 수밖에 없다. 그래서 노브를 여러 개 두지 않고 미리 맞춰둔 셋 중 하나를 고르게 한다.

모드보이는 것대략 폭

숫자만사용 중 조직과 직전 조직의 숫자87pt
코드만사용 중 조직의 코드46pt

막대 모드에서 직전 조직을 함께 보여주지 않는 이유는 폭이다. 대신 전환이 일어나면 코드가 바뀌는 것으로 드러나고, 떠나온 조직의 상태는 눌러서 본다.

숫자만 모드에서는 옆자리가 방금 한도에 걸려 떠나온 조직이다. 전환 뒤 가장 궁금한 것 하나를 담는 자리다. 원래 조직으로 언제 돌아갈 수 있는가.

색은 창마다 따로 붙는다

숫자는 남은 양이다. 메뉴바를 흘깃 보는 목적이 "아직 돌려도 되나" 를 확인하는 것이므로 남은 쪽이 곧바로 답이 되는 숫자다. 클수록 좋다.

막대 모드에서는 막대가 색을 지고 숫자는 기본색으로 둔다. 둘 다 물들이면 노이즈가 된다. 세 창은 서로 독립적으로 바닥나므로 색도 따로 붙는다.

요청 흐름

요청 하나가 들어와서 나갈 때까지. 가장 중요한 제약은 5단계에 있다.

요청 본문을 통째로 보관한다
다시 보내려면 사본이 있어야 한다. 8 MB 를 넘으면 사본을 포기하고 전환도 포기한다.
모델과 세션을 읽는다
본문에서 모델 이름을, 헤더에서 세션 식별자를 꺼낸다. 처음 보는 세션이면 새 대화로 본다.
조직을 고른다
자동 전환에서 빼둔 조직을 먼저 거르고, 인증 실패와 쿨다운 중인 조직을 걸러낸다. 여유 없는 조직은 뒤로 민다.
자격증명을 붙여 보낸다
클라이언트 인증 정보를 지우고 Keychain 자격증명을 넣는다. 만료가 가까우면 먼저 갱신한다.
첫 조각만 열어본다
스트리밍 응답이면 첫 조각까지만 받아 한도 오류인지 판별한다. 여기까지 클라이언트에는 아직 한 바이트도 보내지 않았다. 오류면 3번으로 돌아가 다음 조직을 쓴다. 이 한 줄이 전체 설계를 결정한다.
흘려보낸다
통과로 판정되면 첫 조각부터 클라이언트로 내보내고 나머지를 이어서 중계한다. 이 시점 이후로는 다시 판정하지 않는다.
기록한다
토큰 사용량과 잔여 한도를 남긴다. 전환이 있었다면 그 시각도 함께.
인증 오류는 조직을 태우지 않는다

자격증명이 만료돼 401 을 맞으면 갱신을 한 번 하고 같은 조직으로 다시 시도한다. 사용자는 아무것도 눈치채지 못한다. 갱신이 네트워크 문제로 실패하면 그 조직을 무효화하지 않고 이번 요청만 다음 조직으로 넘긴다.

모든 조직이 막혔다면

마지막으로 받은 실패 응답을 그대로 클라이언트에 전달한다. clfl 이 만든 가짜 오류가 아니라 서버가 실제로 준 응답이라야, 사용자가 보는 메시지와 실제 상황이 어긋나지 않는다.

먼저 확인할 것

구현 순서에서 첫 관문은 전환 없이 통과만 시키는 프록시로 데스크톱 앱 대화가 되는지다. 거기서 MCP 도구 검색과 원격 제어 제약이 실제로 어떻게 나타나는지, 대화 시작을 판별할 세션 식별자가 오는지가 한꺼번에 드러난다.

그 앞 단계까지는 네트워크 없이 만든다. 헤더 변환, 응답 분류, SSE 경계 스캐너, 선택 알고리즘, 저장소. 실제 자격증명 없이도 절반 이상을 만들고 검증할 수 있다.

clfl 설계 문서. 이 페이지는 요약이고 구현에 쓰는 것은 docs/design/ 와 docs/porting/ 의 마크다운이다.
