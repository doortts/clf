앱 스스로 새 버전으로 갈아타기

clf 는 지금 저장소를 받아 ./scripts/install-app.sh 를 다시 돌려야 새 버전이 된다. 쓰는 사람이 저장소를 계속 들여다볼 이유는 없으니 앱이 스스로 릴리즈를 보고 갈아타게 만든다. 뼈대는 flutterApps/github_client (yonagit) 의 lib/src/update/ 를 옮기되 clf 는 창이 없는 메뉴바 앱이고 배포처가 공개 저장소라서 절반은 덜어낸다.

두 번 고쳤다. 처음에는 임시 서명에 zip 배포를 전제로 썼고, 공증과 DMG 로 가면서 한 번 고쳤다. 이번에는 yonagit 의 릴리즈 스크립트까지 읽고 고친다. 클라이언트 코드만 봤을 때는 안 보이던 것들이 거기 있었다. 잘 풀렸을 때의 순서가 아니라 안 풀렸을 때 무엇이 남는가 가 그것이다.

세 가지가 뒤에 바뀌었다. 17-repo-split.html 이 이 문서보다 우선하는 대목이다.
1. 저장소가 둘로 갈렸다. 확인과 내려받기는 공개 github.com/doortts/clf 그대로지만 릴리즈 노트, 직접 받기, 이슈 같은 사람용 링크는 사내 GHE 로 간다.
2. 4절 시안의 확인 체크박스를 없앴다. 확인은 늘 돈다. 7절 의 autoCheckUpdate 도 만들지 않는다.
3. 지금 확인 단추가 업데이트 제목 옆 새로고침 아이콘이 됐다. 업데이트 구역의 현재 화면은 17 문서 5절이다.

1. 가져올 것과 버릴 것

github_client 의 UpdateService 는 621줄이다. 그 중 우리에게 필요한 구조는 상태 기계와 helper 스크립트 두 개뿐이다.

github_clientclf 에서
상태 기계 (idle, checking, upToDate, available, downloading, ready, error) 그대로 화면이 그릴 것과 다음에 할 수 있는 일이 상태 하나로 정해진다
semver 비교 (compareVersions, pre-release 와 build metadata 무시) 그대로 순수 함수라 테스트가 싸다. ClfDesktop 에 둔다
helper bash 스크립트로 번들 교체 후 재실행 그대로 자기를 지우고 자기를 복사할 수는 없다. 밖에서 기다리는 손이 있어야 한다
DMG 마운트 staging (hdiutil attach -nobrowse, 복사, detach) 그대로 clf 도 공증받은 DMG 로 배포한다. 명시적 mountpoint 를 주는 방식까지 같이 가져온다
zip 경로와 DMG 경로를 같은 모양으로 맞추기 버린다 자산은 DMG 하나다. 두 경로를 맞추려고 있던 분기가 사라진다
OS별 자산 고르기 (dmg, exe, msi, zip 우선순위) 버린다 macOS 전용 앱이다. clf-*.dmg 하나를 이름으로 찾는다
xattr -dr com.apple.quarantine 버린다 공증받고 스테이플한 번들은 격리 딱지가 붙어 있어도 Gatekeeper 를 통과한다. 딱지를 떼는 것은 검사를 건너뛰는 일이라 공증을 받는 쪽과 방향이 반대다
없음 더한다 spctl -a 로 내려받은 번들을 교체 전에 평가한다. 공증 티켓이 붙어 있어야만 제자리에 넣는다
Authorization: token 헤더와 호스트 일치 검사 버린다 github.com/doortts/clf 은 공개 저장소다. 익명으로 읽는다
~/Downloads 에 staging 폴더를 만들고 Finder 로 띄우기 버린다 드래그 인스톨을 안내할 창이 없다. 받은 것은 임시 폴더에 두고 앱이 직접 교체한다
/Applications/Yonagit.app 고정 경로 바꾼다 clf 는 ~/Applications 에 산다. 경로를 박지 않고 Bundle.main.bundleURL 제자리에 넣는다
새 버전 알림을 SnackBar 로 바꾼다 메뉴바 앱에는 SnackBar 자리가 없다. 톱니에 점 하나를 올린다

2. 버전은 어디서 오나

scripts/make-app.sh 는 이미 git describe --tags --always 를 CFBundleShortVersionString 에 넣는다. 그런데 이 저장소에는 태그가 하나도 없어서 지금 값은 커밋 해시다. 자기 버전을 semver 로 못 읽으면 비교할 것이 없다. 

태그가 있을 때   v0.4.0            -> 0.4.0     비교한다
태그 뒤 커밋     v0.4.0-3-gabc123  -> 0.4.0-3   개발 빌드. 확인 자체를 건너뛴다
태그가 없을 때   abc1234 / dev     -> 파싱 실패  개발 빌드. 확인 자체를 건너뛴다

개발 빌드에서 조용히 있는 것이 중요하다. 손으로 빌드해 쓰는 사람에게 릴리즈 버전으로 되돌리자고 권하면 방금 만든 것이 지워진다. 태그와 정확히 같은 커밋에서 빌드한 것만 업데이트 대상으로 본다.

서명이 임시 서명에서 Developer ID 로 바뀐다

scripts/make-app.sh 는 지금 codesign --force --sign - 로 임시 서명만 한다. 공증을 받으려면 세 가지가 더 필요하다. 

codesign --force --options runtime --timestamp \
         --sign "Developer ID Application: ..." .build/clf.app
  • --options runtime: hardened runtime. 없으면 공증이 거절된다
  • --timestamp: 보안 타임스탬프. 인증서가 만료된 뒤에도 서명이 유효하다
  • 인증서 이름은 스크립트에 박지 않는다. 키체인에서 찾고, 못 찾으면 임시 서명으로 떨어져 로컬 빌드가 계속 돌아간다. CLF_SIGN_IDENTITY 로 덮어쓸 수 있다
# 인증서를 키체인에서 찾는다. 릴리즈 때마다 긴 이름을 손으로 넘길 이유가 없다
IDENTITY="${CLF_SIGN_IDENTITY:-$(security find-identity -v -p codesigning \
  | grep "Developer ID Application" | head -1 | sed -E 's/.*"(.+)"$/\1/')}"
clf 에는 없는 문제 하나. yonagit 의 릴리즈 스크립트는 프레임워크와 standalone dylib 을 안에서 바깥으로 하나씩 다시 서명한다. Flutter 빌드가 마지막 단계에서 실행 파일을 타임스탬프 없이 다시 서명해 버려서 공증이 거절되기 때문이다. clf 는 실행 파일 하나짜리 번들이라 그 단계가 통째로 없다. 중첩 서명이 없다는 것이 이 앱의 이점이고, 나중에 의존성이 번들 안에 들어오면 그때 같은 처리가 필요해진다.

릴리즈 절차. 짓는 것과 내보내는 것을 가른다

공증은 앱과 DMG 두 번 받는다. DMG 만 스테이플하면 사용자가 앱을 꺼낸 뒤에는 티켓이 따라오지 않는다. 우리 업데이트 경로는 DMG 에서 .app 을 꺼내 쓰므로 앱에 붙은 티켓이 정작 중요한 쪽이다.

내보내기는 별도 플래그다. 처음 설계는 태그부터 GitHub 릴리즈까지 한 명령에 묶었는데, 실제로 공증만 해 보려니 그 명령을 쓸 수가 없었다. 공증은 되돌릴 수 있고 태그 push 와 릴리즈 생성은 아니다. 되돌릴 수 없는 쪽만 --publish 뒤로 옮긴다. yonagit 이 같은 모양이고, 그쪽은 --skip-notarize 까지 둬서 포장 경로만 몇 초에 시험한다. 

scripts/release.sh v0.1.0                   # 짓고 공증하고 스테이플까지
scripts/release.sh v0.1.0 --publish         # 거기에 태그 push + 릴리즈 생성
scripts/release.sh v0.1.0 --skip-notarize   # 공증 없이 포장만. 몇 초
# 1. 앱 공증. notarytool 은 폴더를 안 받으므로 zip 으로 싸서 올린다.
#    올리는 용도일 뿐이고 이 zip 은 릴리즈에 안 붙는다
ditto -c -k --keepParent .build/clf.app .build/notarize.zip

# 보내기 전에 서명을 먼저 본다. 공증은 왕복에 몇 분이 걸리는데
# 여기서 걸릴 문제를 거기까지 들고 갈 이유가 없다
codesign --verify --deep --strict --verbose=2 .build/clf.app

OUT=$(xcrun notarytool submit .build/notarize.zip \
        --keychain-profile "$PROFILE" --wait 2>&1) || true
# notarytool 은 Invalid 로 끝나도 종료 코드가 0 일 수 있다. 출력을 본다
grep -q "status: Accepted" <<<"$OUT" || { xcrun notarytool log ...; exit 1; }
xcrun stapler staple .build/clf.app

# 2. 스테이플한 앱으로 DMG 를 만든다. /Applications 심볼릭 링크는 넣지 않는다.
#    clf 는 ~/Applications 에 사는 앱이고 창에 뜬 링크가 그쪽으로 유도한다
STAGE=$(mktemp -d); trap 'rm -rf "$STAGE"' EXIT
ditto .build/clf.app "$STAGE/clf.app"      # cp -R 은 서명과 심볼릭 링크를 흘린다
hdiutil create -volname "clf $TAG" -srcfolder "$STAGE" -ov -format UDZO "$DMG"

# 3. DMG 도 공증한다. 브라우저로 직접 받아 여는 사람이 이 티켓을 본다
#    (같은 제출 함수를 다시 쓴다)

# 4. --publish 일 때만. 여기서부터 되돌릴 수 없다
git tag -a "$TAG" -m "clf $TAG"            # 주석 태그. 누가 언제 냈는지 남는다
git push origin main "$TAG"
gh release create "$TAG" --repo github.com/doortts/clf \
   --title "clf $TAG" --generate-notes "$DMG"
ditto -c -k --keepParent 를 쓰는 이유는 zip 명령이 심볼릭 링크와 확장 속성을 흘려서 서명이 깨지기 때문이다. 공증 업로드용 zip 에서 서명이 깨지면 거절 사유가 서명 없음 으로 나와서 원인을 찾는 데 오래 걸린다. 같은 이유로 DMG staging 도 cp -R 이 아니라 ditto 다.
--repo 를 반드시 적는다. 첫 릴리즈를 시도하다 걸렸다. 이 기계의 gh 는 사내 GHE 호스트에만 로그인되어 있어서 github.com 은 인증된 호스트 목록에 아예 없었다. --repo 없이 부르면 gh 가 어느 호스트로 갈지 스스로 고르는데, 그 판단이 우리가 원한 곳과 다를 수 있다. 저장소를 명시하면 그 애매함이 사라진다. yonagit 도 GHE 를 명시한다.

3. 언제 확인하나

익명 GitHub API 는 IP 당 시간당 60 회다. 사용량 읽기와 달리 릴리즈는 자주 바뀌지 않으니 아낀다.

  • 앱을 켤 때 한 번. 마지막 확인이 24시간 안이면 건너뛴다
  • 그 뒤로는 24시간마다. 이미 도는 갱신 타이머에 얹는다. 타이머를 새로 두지 않는다
  • 톱니를 눌러 설정을 열 때 확인 단추를 손으로 누를 수 있다. 이때는 24시간 규칙을 무시한다
  • 호출은 GET /repos/doortts/clf/releases/latest 하나다. If-None-Match 로 ETag 를 보내면 304 는 한도를 깎지 않는다
실패는 조용히 지나간다. 사용량 읽기가 실패하면 앱이 쓸 데가 없어지지만 업데이트 확인이 실패하는 것은 그냥 다음에 다시 보면 되는 일이다. 팝오버 머리에 빨간 줄을 띄우지 않고, 설정을 열었을 때만 왜 실패했는지 적는다.

5. 갈아타는 순서

자기를 지우면서 자기를 복사할 수는 없다. 그래서 교체는 앱 밖에서 일어난다. 앱은 새 번들을 임시 폴더에 펼쳐 두고, 밖에서 기다릴 스크립트를 띄운 뒤 스스로 종료한다. 

앱 안                                        앱 밖

1. GET /releases/latest
   tag_name 을 자기 버전과 semver 비교
        |
2. 자산 DMG 를 URLSession 으로 받는다
   ~/Library/Caches/clf/update/v0.5.0/clf-v0.5.0.dmg
   30초 동안 새 조각이 안 오면 끊는다
        |
3. hdiutil attach -nobrowse -readonly
           -mountpoint .../v0.5.0/.mount
        |
4. ditto 로 .app 을 캐시 폴더에 꺼내고
   hdiutil detach 로 곧바로 내린다
   .../v0.5.0/clf.app
        |

   accepted, source=Notarized Developer ID
   아니면 여기서 멈춘다
        |

   로그 경로를 남긴 뒤
   Process detached 로 띄운다  ------------>  7. 부모가 죽기를 기다린다
        |                                       (0.5초씩 최대 15초)

                                                번들이 없는 순간이 없다
                                                ditto new -> <bundle>.new
                                                mv <bundle>     <bundle>.old
                                                mv <bundle>.new <bundle>

                                                      |

왜 제자리인가

github_client 는 /Applications/Yonagit.app 을 목표로 박아 뒀다. clf 은 그러면 안 된다.

  • clf 은 ~/Applications 에 산다. 관리자 권한을 요구하지 않으려는 선택이고 docs/design/11-menubar-app.md 의 결정이다. 공증을 받아도 이 자리는 그대로 둔다. 사용자 폴더에 있으면 helper 가 관리자 인증 없이 교체할 수 있어서 자동 업데이트 쪽이 오히려 쉬워진다
  • 로그인 항목 등록은 번들 경로에 매인다. 경로가 바뀌면 SMAppService 등록이 끊어져 사용자가 승인을 다시 해야 한다. 제자리 교체는 그 문제를 아예 만들지 않는다
  • Bundle.main.bundleURL 은 어디서 실행했든 맞는 답을 준다. 경로를 박는 순간 /Applications 에 둔 사람과 ~/Applications 에 둔 사람 중 한쪽이 깨진다

설치를 아예 제안하지 않는 경우

조건대신 하는 일
번들 경로가 .build 안 확인도 안 한다. 개발 빌드다
자기 버전이 semver 가 아님 확인도 안 한다. 태그 없는 빌드다
번들이 든 폴더에 쓰기 권한이 없음 직접 받기 만 보여준다. /Applications 에 관리자가 넣어 둔 경우
DMG 마운트 실패, 또는 안에 clf.app 이 없음 error. 받은 파일이 온전하지 않다. 캐시를 지우고 다시 시도
spctl -a -vv 가 accepted 가 아님 error. 공증 티켓이 없거나 서명이 우리 것이 아니다. 제자리에 넣지 않는다
교체 전 평가가 이 설계의 유일한 안전장치다. 우리는 앱을 자기 자리에 덮어쓰는 권한을 helper 에게 준다. 릴리즈 자산이 바뀌었거나 중간에서 응답이 바뀌었을 때 그것을 걸러낼 곳은 여기뿐이다. HTTPS 와 GitHub 을 믿는 것과 별개로, 실제로 실행할 번들이 우리 Developer ID 로 서명되고 공증받은 것인지 spctl -a -vv <app> 으로 한 번 본다. 출력이 source=Notarized Developer ID 가 아니면 멈춘다.

yonagit 을 읽고 더한 것

위 순서는 잘 풀렸을 때의 이야기다. yonagit 의 업데이트 코드에서 정작 배울 것은 안 풀렸을 때 무엇이 남느냐 쪽이었다. 네 가지를 가져온다.

멈춘 다운로드와 끝나지 않는 것을 구별한다

yonagit 은 응답 스트림에 30초 무활동 타임아웃을 건다. 요청 전체에 거는 타임아웃과 다르다. 사내망이나 프록시가 연결은 열어 둔 채 조각을 안 보내면 전체 타임아웃만으로는 영영 기다리게 되고, 화면에는 진행 막대가 멈춘 채로 남는다. 마지막 조각이 온 뒤 30초가 지나면 끊고 error 로 간다. 마운트와 복사에도 각각 60초를 건다. hdiutil 이 걸리면 사용자는 이유를 알 길이 없다.

helper 는 로그를 남긴다

이것이 가장 큰 배움이다. helper 는 앱이 죽은 뒤에 돈다. 그 시점에는 화면도 없고 우리 프로세스도 없다. 교체가 실패하면 사용자에게는 앱이 다시 안 뜬다 는 사실만 남고 왜인지 알 방법이 없다. yonagit 은 스크립트 첫 줄에서 출력을 통째로 파일에 돌린다. 

#!/bin/bash
set -e
exec >>"$LOG" 2>&1
echo "[$(date)] installer start"

그리고 앱은 helper 를 띄우기 전에 그 경로를 로그로 남긴다. 다시 뜬 앱이 이전 교체가 실패한 것을 발견하면 설정에 그 경로를 보여준다. 로그는 임시 폴더가 아니라 ~/Library/Logs/clf/update-<tag>.log 에 둔다. 임시 폴더는 재부팅에 지워지고, 교체 실패는 재부팅으로 조사하는 종류의 일이다.

실패해도 받은 것은 지우지 않는다

성공하면 캐시 폴더를 지운다. 실패하면 남긴다. 4MB 를 다시 받는 것이 아까워서가 아니라, 자동 설치가 막힌 사람에게 이미 손에 있는 DMG 가 가장 짧은 탈출구이기 때문이다. error 상태에 받은 파일 열기 를 둔다. 누르면 Finder 가 그 DMG 를 띄우고, 그다음은 사람이 끌어다 놓으면 끝난다. yonagit 은 이 자리를 아예 기본 동선으로 쓴다. 우리는 자동 교체를 기본으로 두되 그 문을 닫지는 않는다.

단계마다 사람이 읽을 이유를 남긴다

yonagit 의 DMG staging 은 실패할 수 있는 자리마다 문장을 하나씩 남긴다. DMG 마운트 실패 (exit 1), DMG 안에 앱이 없습니다, .app 복사 실패. 그래야 스낵바에 그대로 띄울 수 있다. 우리도 error 하나로 뭉뚱그리지 않고 어디서 멈췄는지 문장으로 남긴다. 설정 칸은 좁으니 한 줄로 자르고, 전문은 로그 파일에 있다.

6. 위험과 대비

위험왜 생기나대비
공증 티켓이 안 붙은 번들이 나간다 앱을 스테이플하기 전에 DMG 를 만들면 꺼낸 .app 에는 티켓이 없다. 온라인일 때는 그냥 통과해서 릴리즈할 때 눈치채기 어렵다 릴리즈 절차가 앱을 먼저 스테이플하고 그 결과로 DMG 를 만든다. 올린 뒤 spctl -a -vv 로 자기 자산을 한 번 본다. 앱이 교체 직전에 하는 것과 같은 검사다
이전 임시 서명 빌드에서 갈아탈 때 권한이 끊긴다 알림 권한과 로그인 항목 등록은 서명에 매인다. 임시 서명은 기계마다 값이 달라서 Developer ID 서명으로 처음 갈아타는 그 한 번은 시스템이 다른 앱으로 볼 수 있다 공증 이후 버전끼리는 서명이 같아 문제가 없다. 갈아타는 첫 번만 Notifier.refreshPermission 과 loginItem.isChecked 를 확인한다. denied 로 떨어지면 설정에 이미 있는 안내 줄이 그대로 뜬다
교체 중에 앱이 사라진다 rm -rf 로 지운 다음 ditto 로 복사하면 그 사이에 helper 가 죽었을 때 번들이 없는 상태로 남는다. 되돌릴 손이 없다 먼저 <bundle>.new 로 다 복사해 두고 mv 두 번으로 자리를 바꾼다. mv 는 같은 볼륨에서 원자적이라 어느 순간에 멈춰도 실행할 수 있는 번들이 한 자리에 있다
돌고 있는 번들을 덮어쓴다 실행 중인 번들을 갈아 끼우면 다음 실행이 깨진다. install-app.sh 도 같은 이유로 pkill 을 먼저 한다 helper 가 부모 프로세스 종료를 기다린다. 15초 안에 안 죽으면 교체를 포기하고 로그만 남긴다
교체가 실패했는데 이유를 아무도 모른다 helper 는 앱이 죽은 뒤에 돈다. 화면도 없고 우리 프로세스도 없다. 실패하면 사용자에게는 앱이 다시 안 뜬다는 사실만 남는다 helper 가 출력을 통째로 ~/Library/Logs/clf/update-<tag>.log 로 돌린다. 다시 뜬 앱이 이전 교체의 흔적을 발견하면 설정에 그 경로를 보여준다. yonagit 에서 가져온 것 중 가장 값이 나가는 한 줄이다
설치가 두 번 돈다 이미 받아 둔 상태에서 단추를 다시 누르면 내려받기 단계를 건너뛰는데, 그 단계 끝에 붙어 있던 후속 동작이 한 번 더 불릴 수 있다. yonagit 은 이것을 wasAlreadyReady 로 막는다 상태 기계가 막는다. downloading 과 ready 에서는 설치 단추가 다시 눌리지 않고, helper 는 한 번만 띄운다
같은 릴리즈를 계속 권한다 사용자가 지금은 안 바꾸고 싶은데 열 때마다 점이 뜬다 점은 확인한 뒤 새 버전이 있을 때 뜨고 그 태그의 설정 칸을 한 번 본 뒤에는 사라진다. 건너뛴 태그를 설정에 적어 둔다

7. 저장할 값

DesktopPreferences 에 세 칸을 더한다. 옛 파일에 없는 필드는 기본값으로 떨어지므로 version 은 그대로 둔다. 

public var autoCheckUpdate: Bool    = true    // 하루 한 번 확인
public var lastUpdateCheck: Date?   = nil     // 24시간 규칙의 기준
public var seenReleaseTag: String?  = nil     // 점을 지운 태그

ETag 는 설정에 두지 않는다. 캐시 값이라 설정 파일과 수명이 다르다. ~/Library/Caches/clf/update/etag 에 두고 없으면 그냥 다시 받는다.

9. 테스트

Tests/ClfDesktopTests/UpdateCheckTests.swift 하나로 시작한다. 기존 테스트와 같은 방식이다.

  • 0.10.0 이 0.9.0 보다 크다. 문자열 비교면 여기서 깨진다
  • v0.4.0 과 0.4.0 이 같다
  • 0.4.0-3-gabc123 은 릴리즈 버전이 아니다. 확인을 건너뛴다
  • abc1234, dev, 빈 문자열은 파싱 실패로 떨어진다
  • 자산 목록에서 clf-v0.5.0.dmg 를 고르고 clf-v0.5.0.dmg.sha256 은 안 고른다. 확장자로만 보면 .dmg 로 끝나는 것을 찾아야 걸러진다
  • 자산이 하나도 안 맞으면 nil 이고 error 로 가지 않는다. 릴리즈 페이지로 보내면 된다
  • helper 스크립트에 공백과 인용부호가 든 경로를 넣어도 문법이 깨지지 않는다
  • helper 스크립트가 로그 경로로 출력을 돌리는 줄을 담고 있다. 그 줄이 빠지면 실패했을 때 아무것도 안 남으므로 테스트가 잠근다
  • spctl 판정: source=Notarized Developer ID 만 통과한다. source=Developer ID (공증 없음), rejected, 빈 출력은 모두 막는다
  • 24시간 규칙: 마지막 확인이 23시간 전이면 건너뛰고 25시간 전이면 확인한다. Clock 을 주입해 시계를 고정한다

마운트와 교체는 단위 테스트로 확인할 수 없다. 손으로 한 번 본다. 이전 태그로 빌드한 번들을 ~/Applications 에 넣고 실행해서 최신 릴리즈로 갈아타는지, 갈아탄 뒤에 로그인 항목과 알림 권한이 살아 있는지 확인한다. 마운트 지점이 남지 않았는지도 같이 본다. detach 를 빠뜨리면 Finder 사이드바에 볼륨이 쌓인다.

10. 단계

1단계는 절반 끝났다. make-app.sh 의 Developer ID 서명과 release.sh 는 있고, 앱 공증도 한 번 통과시켜 확인했다 (status: Accepted, 스테이플, spctl 이 source=Notarized Developer ID). 격리 딱지를 강제로 붙인 사본도 통과해서, xattr 을 버린 판단이 맞았다는 것까지 봤다. 남은 것은 첫 태그 릴리즈고 notarytool 키체인 프로필이 사라진 상태라 다시 등록해야 한다.
  1. 서명과 공증 파이프라인. make-app.sh 에 Developer ID 서명과 hardened runtime, scripts/release.sh 에 notarytool 과 stapler. 여기에 --publish 와 --skip-notarize 를 더하고 --repo 를 명시한다. 그다음 v0.1.0 을 첫 릴리즈로 올린다. 비교 대상이 없으면 아래 전부가 검증되지 않는다
  2. 확인까지. UpdateCheck.swift 와 테스트, 설정에 지금 확인 단추와 결과 한 줄. 여기까지만으로도 사용자는 릴리즈 페이지에서 DMG 를 받아 갈 수 있다
  3. 자동 확인. 24시간 규칙, ETag, 톱니의 점
  4. 제자리 교체. DMG 마운트와 spctl 평가, helper 스크립트, 설치하고 다시 시작. 쓰기 권한과 평가에서 막히는 경로를 먼저 만든다. 로그 파일과 받은 파일 열기 도 이때 같이 넣는다. 실패했을 때 아무것도 안 남는 상태로 4단계를 내보내면 안 된다

1단계가 제일 무겁고 나머지의 전제다. 공증 없이 2단계부터 손대면 사용자가 받은 DMG 가 확인되지 않은 개발자로 걸려서 확인 기능이 오히려 민원을 만든다. 2단계에서 멈춰도 쓸 만하다. 4단계는 DMG 를 열고 끌어다 놓는 수고를 없애는 것이지 없으면 안 되는 것이 아니다.
