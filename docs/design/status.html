판정 계층(Core)과 저장 계층(Store)이 끝났고, 네트워크 계층(Proxy)에 첫 두 조각 (SSEPeek, UpstreamExecutor)이 들어갔다. 남은 것은 프록시 서버와 스왑 루프다.

1. 검증 사다리

각 칸은 실행할 명령과 통과 기준을 가진다. 윗 칸이 통과해야 아랫 칸으로 간다. 완성 전에 손으로 밟을 수 있어야 한다는 것이 규칙이다.

1-5 ClflCore 판정 로직 swift test --filter ClflCoreTests  ->  117개 통과
6 ClflStore 저장 계층 swift test --filter ClflStoreTests  ->  54개 통과
6a 환경 점검 clflctl doctor  ->  실패 항목 0
6b 조직 등록 clflctl accounts add  ->  list 에 뜨고 Keychain 에 있음
6c 설정 주입 clflctl settings install  ->  show 가 주입됨을 말한다
6d 선택 판정 clflctl runtime simulate + select  ->  표가 예상과 같다
6e 응답 분류 clflctl classify  ->  네 경로가 갈린다
6f SSE 경계 clflctl sse-peek  ->  주석 프레임을 건너뛴다
7 업스트림 왕복 clflctl upstream probe <id>  ->  실제 200 과 사용량 헤더
8 프록시 단일 조직 통과 clflctl serve --single <id>  ->  Claude Code 데스크톱 앱으로 대화 성공
9 스왑 serve + runtime simulate  ->  스왑 발생, 트레일에 기록
10 컨트롤 플레인 clflctl watch  ->  스왑이 실시간으로 흐른다
11 메뉴바 앱 Xcode  ->  메뉴바에 같은 값이 뜬다

8번이 첫 관문이다. 여기서 MCP 도구 검색 제약과 X-Claude-Session-Id 헤더 존재 여부가 실제로 드러난다. 그 앞에 손으로 밟을 디딤돌 여섯 개(6a-6f)를 먼저 놓은 이유다.

3. 구조

화살표는 의존하는 쪽에서 의존받는 쪽으로 향한다. 실선 상자가 완성, 점선이 미구현이다. ClflCore 에 의존성을 하나도 두지 않은 것이 이 구성의 핵심이다. NIO 가 한 번 들어오면 테스트가 이벤트 루프를 요구하기 시작한다.

4. 내부 상태를 검증하는 도구

메뉴바 앱은 관찰하기 나쁜 실행 환경이다. 화면이 좁고, 스왑은 200ms 안에 끝나며, 한도에 실제로 걸릴 때까지 기다릴 수 없다. 그래서 관찰과 조작을 앱 밖으로 뺐다.

요청 전

clflctl

터미널에서 단계를 실행한다. 앱 번들도 Xcode 도 없이 돈다. 지금 요청이 오면 어디로 갈지 미리 판정해 본다.

요청 중

컨트롤 플레인

프록시가 도는 동안 내부 상태를 읽는 읽기 전용 HTTP. 설계만 끝났고 붙일 상태가 아직 없다.

요청 후

jsonl 로그

usage.jsonl 과 audit.jsonl 을 조인한다. 스왑이 유발한 캐시 재생성 비용이 여기서 나온다.

같은 레코드 원칙

관찰용 코드가 실제 판정과 다른 답을 내면 없느니만 못하다. 그래서 판정 함수가 이유를 값으로 낸다. select() 는 explain() 의 얇은 껍질이다.

// 위 표, 컨트롤 플레인의 GET /select, 요청 트레일의 candidates 가 전부 이 하나다 public func select(_ input: SelectionInput) -> SelectionResult { explain(input).result } public func explain(_ input: SelectionInput) -> SelectionExplanation

두 경로로 갈라 두면 설명이 언제든 거짓말을 시작한다. test_explainAgreesWithSelect 가 그것을 잠근다. 표에 찍히는 여유 값도 표시용으로 다시 계산한 것이 아니라 강등 판정이 실제로 쓴 값 그대로다.

상태를 손으로 심는다

한도에 걸리기를 기다릴 수 없으므로 런타임 상태를 만들어 넣고 판정을 다시 돌린다.

$ clflctl runtime simulate naver_team_40 --rate-limit 600 naver_team_40 상태를 바꿨다. clflctl select 로 확인한다 $ clflctl select 순위 id 판정 여유 이유 ---- ------------- ---- ---- ------------------------------------ 1 naver_team_40 제외 - claude-opus-4-5 쿨다운 19:40:08 까지 2 naver_team_52 선택 3% 선택 3 ent1 후보 - 대기 (tier 1) 결과 naver_team_52 (team)

격리

실험이 실제 설정을 건드리면 안 된다. 디렉토리만 바꾸면 격리가 반쪽이다. 자격증명은 여전히 진짜 Keychain 으로 간다. 그래서 서비스 이름도 연다.

$ clflctl select \ --data-dir /tmp/clfl-demo/data \ --claude-dir /tmp/clfl-demo/claude \ --keychain-service me.clfl.demo

5. 컨트롤 플레인

프록시가 도는 동안 내부 상태를 읽는 읽기 전용 HTTP 표면이다. 프록시 포트에 /_clfl/... 같은 경로를 얹지 않고 별도 포트를 쓴다.

왜 별도 포트인가

  • 표면이 겹친다. Anthropic API 밖의 경로를 가로채기 시작하면 클라이언트가 새 엔드포인트를 쓸 때 조용히 충돌한다
  • 수명이 다르다. 프록시가 포트 바인딩에 실패한 순간이 바로 상태를 봐야 할 때인데, 거기 매달려 있으면 아무것도 못 본다
  • 노출을 묶지 않는다. 하나가 새면 둘 다 샌다

보안

  • 127.0.0.1 에만 바인딩
  • 읽기 전용. 상태를 바꾸는 경로가 없다
  • 자격증명을 싣지 않는다. RouterSnapshot 타입 자체가 토큰을 갖지 않는다
  • 기본 꺼짐. 켠 사람만 대가를 진다
GET내용
/health떠 있는지, 프록시가 어느 포트에 붙었는지, 얼마나 됐는지
/stateRouterSnapshot. 조직, 우선순위, 런타임, 활성, 지속 조건
/select?model=&start=지금 요청이 오면 어디로 가는지. 4절 표와 같은 레코드
/requests?limit=50최근 요청의 결정 트레일. 메모리 링 버퍼 200개
/eventsSSE. 스냅샷 변화와 RoutingEvent 를 실시간으로

audit.jsonl 과 무엇이 다른가

audit.jsonl 은 사건을 남기고 트레일은 판단 과정을 남긴다. 스왑이 일어난 것은 audit 에 있지만, 왜 team2 를 건너뛰고 ent1 로 갔는지는 없다.

{"at":"...","sessionId":"...","model":"claude-opus-4-5", "candidates":[{"id":"team1","disposition":"cooling","headroom":null}, {"id":"team2","disposition":"chosen","headroom":0.41}], "attempts":[{"account":"team1","status":429,"errorType":"rate_limit_error"}, {"account":"team2","status":200,"ttfbMillis":840}], "outcome":"swapped"}

6. 남은 작업

7단계 완료   UpstreamExecutor + SSEPeek

TDD. 테스트 41개

압축 자동 해제를 켰고, mtime 을 고정한 gzip 바이트를 fixture 에 박아 잠갔다. 해제가 꺼지면 peek 이 gzip 을 읽어 테스트가 즉시 빨개진다. 문서 경고만으로는 언젠가 누가 끈다.

TDD 가 넷을 잡았다. 스캐폴딩 enum 이 릴레이를 불가능하게 만들고 있었고 (남은 스트림을 들지 않았다), 연결 타임아웃 기본값 10초가 스왑 grace 예산을 넘겼고, peek 의 선행 읽기 없음을 내가 버그로 오해했고, 가짜 업스트림이 헤더 경계를 문자 수로 세고 있었다. 자세한 것은 08-verification 7-1절.

첫 관문   8단계. ProxyServer 단일 조직

다음 차례. ClflProxy 3개 파일

스왑 없이 한 조직으로만 통과시킨다. 여기서 세 가지가 처음 드러난다. MCP 도구 검색을 되살린 것이 실제로 먹히는지, X-Claude-Session-Id 헤더가 오는지, 원격 제어 제약이 어떻게 나타나는지.

통과 기준: Claude Code 데스크톱 앱으로 대화가 성립한다

7. 도구가 이미 잡아낸 것

검증 계층을 만들자마자 셋이 드러났다. 이것이 앱보다 도구를 먼저 만드는 이유다.

발견처리
취소된 debounce 타이머가 한 번 더 썼다. try? await Task.sleep 이 취소를 삼키고 그대로 진행해서, flush() 가 막 쓴 파일 위에 유령 쓰기가 겹쳤다 고침 남은 임시 파일을 테스트가 잡아냈다
상태 코드만으로는 스왑하지 않는다. 본문 없이 429 만 주면 통과 판정이 나온다. 분류기가 옳지만 도구가 이유를 말하지 않았다 고침 추출한 error.type 을 항상 함께 찍는다
tier 1 안의 순서가 미정이다. 잔여 3% 인 조직이 읽기 없는 조직보다 앞선다. 둘 다 tier 1 이고 우선순위가 앞서기 때문이다 보류 실측 없이 정하지 않는다
열린 질문. 3% 짜리 조직은 거의 확실히 429 를 맞는다. 읽기가 없는 조직은 알 수 없다. 아는 실패와 모르는 상태를 같은 칸에 두고 우선순위로 자르면, 곧 실패할 것을 알면서 그쪽으로 보내는 셈이다. 반응형 경로가 받아내지만 캐시는 이미 잃는다.

갈래 하나 - 지금 그대로 둔다. 우선순위는 사용자 의사이고, 읽기가 없다는 것은 안 써봤다는 뜻일 수 있다. 갈래 둘 - tier 1 을 쪼개서 읽기 없음을 잔여 낮음보다 앞에 둔다. 선제 강등이 대화 시작에만 걸리므로 영향 범위가 좁다.

usage.jsonl 과 audit.jsonl 을 조인하면 스왑이 유발한 캐시 재생성 비용이 실측으로 나온다. 8단계 이후에 정한다.
