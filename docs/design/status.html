1. 검증 사다리

각 칸은 실행할 명령과 통과 기준을 가진다. 윗 칸이 통과해야 아랫 칸으로 간다. 완성 전에 손으로 밟을 수 있어야 한다는 것이 규칙이다.

8번에서 막혔다. 그 칸을 지우지 않고 남긴다. 사다리는 통과 기록이자 실패 기록이다.

1-5 ClfCore 판정 로직 swift test --filter ClfCoreTests  ->  117개 통과
6 ClfStore 저장 계층 swift test --filter ClfStoreTests  ->  54개 통과
6a 환경 점검 clfctl doctor  ->  실패 항목 0
6b 계정 등록 clfctl accounts add  ->  list 에 뜨고 Keychain 에 있음
6c 설정 주입 clfctl settings install  ->  show 가 주입됨을 말한다

8번이 첫 관문이었고 거기서 갈렸다. 데스크톱 앱은 프록시를 안 탄다. 프로세스 환경에까지 ANTHROPIC_BASE_URL 을 넣고 시험했지만 요청 0건이었고 앱 로그에는 apiHost: 'https://api.anthropic.com' 이 찍혔다.

처음에는 약한 근거로 막혔다고 단정했다. 자식 프로세스 환경을 물려받았을 수도 있었고, 관리 대상 변수 목록은 앱의 설정 화면을 다스릴 뿐 부모 환경을 다스리지 않는다. 되묻는 질문을 받고서야 제대로 시험했다. 사다리를 놓은 값어치가 여기 있었다.

3. 구조

화살표는 의존하는 쪽에서 의존받는 쪽으로 향한다. ClfCore 에 의존성을 하나도 두지 않은 것이 이 구성의 핵심이다. NIO 가 한 번 들어오면 테스트가 이벤트 루프를 요구하기 시작한다.

ClfDesktop 과 ClfProxy 는 서로 모른다. 트랙이 다르다. 앱은 Desktop 만 쓴다.

4. 내부 상태를 검증하는 도구

메뉴바 앱은 관찰하기 나쁜 실행 환경이다. 화면이 좁고, 스왑은 200ms 안에 끝나며, 한도에 실제로 걸릴 때까지 기다릴 수 없다. 그래서 관찰과 조작을 앱 밖으로 뺐다.

요청 전

clfctl

터미널에서 단계를 실행한다. 앱 번들도 Xcode 도 없이 돈다. 지금 요청이 오면 어디로 갈지 미리 판정해 본다.

요청 중

컨트롤 플레인

프록시가 도는 동안 내부 상태를 읽는 읽기 전용 HTTP. 설계만 끝났고 붙일 상태가 아직 없다.

요청 후

jsonl 로그

usage.jsonl 과 audit.jsonl 을 조인한다. 스왑이 유발한 캐시 재생성 비용이 여기서 나온다.

같은 레코드 원칙

관찰용 코드가 실제 판정과 다른 답을 내면 없느니만 못하다. 그래서 판정 함수가 이유를 값으로 낸다. select() 는 explain() 의 얇은 껍질이다.

// 위 표, 컨트롤 플레인의 GET /select, 요청 트레일의 candidates 가 전부 이 하나다 public func select(_ input: SelectionInput) -> SelectionResult { explain(input).result } public func explain(_ input: SelectionInput) -> SelectionExplanation

두 경로로 갈라 두면 설명이 언제든 거짓말을 시작한다. test_explainAgreesWithSelect 가 그것을 잠근다. 표에 찍히는 여유 값도 표시용으로 다시 계산한 것이 아니라 강등 판정이 실제로 쓴 값 그대로다.

상태를 손으로 심는다

한도에 걸리기를 기다릴 수 없으므로 런타임 상태를 만들어 넣고 판정을 다시 돌린다.

$ clfctl runtime simulate naver_team_40 --rate-limit 600 naver_team_40 상태를 바꿨다. clfctl select 로 확인한다 $ clfctl select 순위 id 판정 여유 이유 ---- ------------- ---- ---- ------------------------------------ 1 naver_team_40 제외 - claude-opus-4-5 쿨다운 19:40:08 까지 2 naver_team_52 선택 3% 선택 3 ent1 후보 - 대기 (tier 1) 결과 naver_team_52 (team)

격리

실험이 실제 설정을 건드리면 안 된다. 디렉토리만 바꾸면 격리가 반쪽이다. 자격증명은 여전히 진짜 Keychain 으로 간다. 그래서 서비스 이름도 연다.

$ clfctl select \ --data-dir /tmp/clf-demo/data \ --claude-dir /tmp/clf-demo/claude \ --keychain-service me.clf.demo

설치

.build/debug/clfctl 은 상대 경로라 저장소 밖에서 부를 수 없고, 빌드를 다시 돌리면 자리가 바뀔 수 있다. 릴리스로 빌드해 PATH 에 링크한다.

$ ./scripts/install-clfctl.sh 빌드하는 중 링크했다 ~/.local/bin/clfctl

5. 컨트롤 플레인

터미널 트랙이다. 프록시가 도는 동안 내부 상태를 밖에서 읽기 위한 것이라 메뉴바 앱에는 필요 없다. 앱은 5분마다 스스로 읽고 팝오버가 곧 그 상태다. 프록시를 제품으로 내놓을 때 마저 만든다.

프록시가 도는 동안 내부 상태를 읽는 읽기 전용 HTTP 표면이다. 프록시 포트에 /_clf/... 같은 경로를 얹지 않고 별도 포트를 쓴다.

왜 별도 포트인가

  • 표면이 겹친다. Anthropic API 밖의 경로를 가로채기 시작하면 클라이언트가 새 엔드포인트를 쓸 때 조용히 충돌한다
  • 수명이 다르다. 프록시가 포트 바인딩에 실패한 순간이 바로 상태를 봐야 할 때인데, 거기 매달려 있으면 아무것도 못 본다
  • 노출을 묶지 않는다. 하나가 새면 둘 다 샌다

보안

  • 127.0.0.1 에만 바인딩
  • 읽기 전용. 상태를 바꾸는 경로가 없다
  • 자격증명을 싣지 않는다. RouterSnapshot 타입 자체가 토큰을 갖지 않는다
  • 기본 꺼짐. 켠 사람만 대가를 진다
GET내용
/health떠 있는지, 프록시가 어느 포트에 붙었는지, 얼마나 됐는지
/stateRouterSnapshot. 계정, 우선순위, 런타임, 활성, 지속 조건
/select?model=&start=지금 요청이 오면 어디로 가는지. 4절 표와 같은 레코드

audit.jsonl 과 무엇이 다른가

audit.jsonl 은 사건을 남기고 트레일은 판단 과정을 남긴다. 스왑이 일어난 것은 audit 에 있지만, 왜 team2 를 건너뛰고 ent1 로 갔는지는 없다.

6. 남은 작업

완료   사용량 읽기

ClfDesktop. 테스트 60여개

데스크톱 앱의 config.json 에서 계정별 OAuth 토큰을 꺼낸다. 거기 담긴 토큰에는 user:profile 스코프가 있어 Usage API 를 부를 수 있다. setup-token 이 주는 토큰으로는 403 이다.

추론 요청이 아니라 토큰을 소모하지 않는다. 그래서 주기적으로 물어도 된다. 앱에서 한 번이라도 연 계정은 활성이 아니어도 읽힌다.

완료   메뉴바 앱

SPM 실행 타겟 + make-app.sh

Xcode 프로젝트를 두지 않았다. 번들에 필요한 것은 실행 파일과 Info.plist 와 임시 서명뿐이라 스크립트가 조립한다. 프로젝트를 두면 타겟 정의가 Package.swift 와 갈라지고 커맨드라인 빌드가 막힌다.

실기기에서 확인했다. 막대에 84% 가 떴고 clfctl 과 같은 숫자다. Bartender 5 가 항목을 숨김 영역으로 보내서 눈으로는 못 보고 접근성 API 로 읽었다.

./scripts/install-app.sh 다음 open ~/Applications/clf.app

완료   설정, 갱신 주기, 로그인 항목

전부 TDD

설정은 보여줄 것이 아니라 숨길 것을 담는다. 보여줄 목록만 저장하면 계정이 새로 생겼을 때 설정을 열기 전까지 영영 안 보인다.

갱신은 5분이 기본이고 세 번 연속 그대로면 10분으로 늘린다. 429 를 받으면 15분으로 물러선다. 읽기 실패와 429 는 다르다. 못 읽는 것은 빨리 되물어야 하고 막힌 것은 물러나야 한다.

다음   앱 아이콘과 배포

남은 것이 이것뿐이다

번들에 아이콘이 없다. 그리고 지금은 임시 서명이라 다른 기계에 옮기면 Gatekeeper 가 막는다. 남에게 줄 생각이면 공증이 필요하다.

완료   계정마다 창 하나, 그리고 세션 넘기기

AltInstance, AltLauncher, SessionMirror, SessionHandoff

데스크톱 앱은 CLAUDE_USER_DATA_DIR 로 데이터 디렉토리를 바꿀 수 있고 단일 인스턴스 잠금이 없다. 그래서 계정마다 창을 하나씩 띄운다. 씨앗은 44K 다. 쿠키에 계정을 미리 박아 두므로 새 창에서 다시 로그인하지 않는다.

넘기기는 대화를 복사하지 않는다. 대화는 ~/.claude/projects 에 있고 계정 표시가 없다. 어느 계정 것인지는 420바이트짜리 레코드가 어느 폴더에 있느냐로만 정해지므로, 그 파일 하나를 옮기면 끝난다. 크기도 진행 상태도 상관없다.

보류   터미널 트랙 프록시

ClfProxy 13파일. 테스트는 통과

가짜 업스트림에 붙여 gzip SSE 릴레이와 헤더 병합과 세션 id 기록까지 확인했다. Router 도 돈다. 제품으로 내놓지 않는 것뿐이고 고장 난 것이 아니다.

지우지 않는다. 동작하고, 테스트가 지식을 담고 있고, 언젠가 쓸 수 있다. RequestPipeline 스왑 루프가 남았다.

7. 도구가 이미 잡아낸 것

검증 계층을 만들자마자 셋이 드러났다. 이것이 앱보다 도구를 먼저 만드는 이유다.

발견처리
취소된 debounce 타이머가 한 번 더 썼다. try? await Task.sleep 이 취소를 삼키고 그대로 진행해서, flush() 가 막 쓴 파일 위에 유령 쓰기가 겹쳤다 고침 남은 임시 파일을 테스트가 잡아냈다
상태 코드만으로는 스왑하지 않는다. 본문 없이 429 만 주면 통과 판정이 나온다. 분류기가 옳지만 도구가 이유를 말하지 않았다 고침 추출한 error.type 을 항상 함께 찍는다
붙여넣기가 자격증명을 오염시켰다. 터미널에서 토큰을 복사하니 Powerline 장식(U+E0B2)과 줄바꿈이 딸려왔다. 파이프로 넘겨도 setup-token 이 ANSI 제어 문자(U+001B)를 뿜는다 고침 도구가 뽑아낸다. 아래 참조
security 가 값을 16진수로 냈다. 출력 불가 바이트가 하나라도 있으면 원문 대신 hex 를 낸다. 태그가 L: 대신 4c 로 읽혔다 고침 hex 출력을 알아보고 되돌린다
tier 1 안의 순서가 미정이다. 잔여 3% 인 계정이 읽기 없는 계정보다 앞선다. 둘 다 tier 1 이고 우선순위가 앞서기 때문이다 보류 실측 없이 정하지 않는다

자격증명 위생

실제로 겪은 경로라 값이 있다. 오염된 토큰을 저장하면 업스트림이 401 을 내고 사용자는 토큰이 틀렸다고 생각한다. 등록 시점에 막는 편이 훨씬 싸다.

$ claude setup-token | clfctl accounts add naver_team_40 --plan team 정리 제어 문자와 장식을 걷어내고 토큰을 뽑았다 종류 setup-token 등록했다 naver_team_40 (team) $ # 뽑아낼 수 없으면 이유를 말한다 Error: 붙여넣기에 토큰이 아닌 문자가 섞였다. U+E0B2 가 17번째에 있다

값을 고치지는 않는다. 찾아낼 뿐이다. 후보가 정확히 하나일 때만 통과시킨다. 서로 다른 토큰이 둘이면 어느 것인지 우리가 고를 수 없으므로 거부한다. 제어 문자는 지우지 않고 공백으로 바꾼다. 그냥 지우면 앞뒤 조각이 붙어 없던 토큰이 만들어진다.

열린 질문. 3% 짜리 계정은 거의 확실히 429 를 맞는다. 읽기가 없는 계정은 알 수 없다. 아는 실패와 모르는 상태를 같은 칸에 두고 우선순위로 자르면, 곧 실패할 것을 알면서 그쪽으로 보내는 셈이다. 반응형 경로가 받아내지만 캐시는 이미 잃는다.

갈래 하나 - 지금 그대로 둔다. 우선순위는 사용자 의사이고, 읽기가 없다는 것은 안 써봤다는 뜻일 수 있다. 갈래 둘 - tier 1 을 쪼개서 읽기 없음을 잔여 낮음보다 앞에 둔다. 선제 강등이 대화 시작에만 걸리므로 영향 범위가 좁다.

usage.jsonl 과 audit.jsonl 을 조인하면 스왑이 유발한 캐시 재생성 비용이 실측으로 나온다. 8단계 이후에 정한다.
