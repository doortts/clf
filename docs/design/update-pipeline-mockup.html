자동 업데이트 전체 과정 한 장

만드는 쪽과 쓰는 쪽이 릴리즈 저장소 하나로 만난다. 아래 세 띠가 그 전부다. 보라는 내 기계에서 도는 일, 노랑은 저장소에 놓이는 것, 파랑은 사용자 기계에서 도는 일이다. 빨간 테두리 칸은 통과 못 하면 거기서 멈추는 관문이다.

1. 릴리즈 파일은 어디로 가나

지금 이 저장소에는 원격이 둘이다. 어느 쪽인지 정하지 않으면 나머지 설계가 흔들린다. 확인한 사실부터.

원격주소확인한 것
origin github.com/doortts/clf 비공개다. 익명으로 릴리즈 API 를 부르면 404 다. 토큰을 넣어 물어보니 private: true 로 답한다. 지금까지 커밋과 README 는 여기로 올라갔다
oss oss.navercorp.com/sw-chae/clf 사내 GHE. gh 가 이 호스트에 로그인되어 있다. 지금은 정기 점검 중이라 403 이 돌아와 상태를 못 봤다
설계 문서의 전제가 틀렸다. 14 문서는 "github.com/doortts/clf 은 공개 저장소다. 익명으로 읽는다" 라고 적고, 그 전제로 yonagit 의 토큰 처리 코드를 버렸다. 그런데 저장소가 비공개라 익명으로는 릴리즈를 못 읽는다. 둘 중 어디로 가든 이 문제는 남는다. 사내 GHE 도 로그인 없이는 못 읽는다.

그래서 갈림길이 하나 생긴다

clf 는 GitHub 클라이언트가 아니다. Claude 데스크톱 앱의 토큰을 읽을 뿐이고 GitHub 자격증명은 하나도 갖고 있지 않다. yonagit 은 이 문제가 없었다. 그 앱은 사용자가 이미 GHE 에 OAuth 로그인한 상태라 그 토큰을 그대로 빌려 쓴다.

길무엇이 달라지나
A. 저장소를 공개로 설계가 지금 문서 그대로 선다. 익명 호출, 토큰 없음, 코드가 가장 적다. 소스를 공개해도 되는지가 유일한 질문이다
B. 릴리즈만 공개 저장소로 소스는 비공개로 두고 doortts/clf-releases 같은 빈 공개 저장소를 만들어 DMG 만 올린다. 코드 변화는 저장소 이름 한 줄뿐이다
C. 사내 GHE 에 올리고 토큰을 받는다 사용자가 설정에 개인 토큰을 붙여넣어야 한다. 메뉴바 도구에 그걸 시키는 것은 무겁고, 토큰 저장까지 우리 몫이 된다. yonagit 의 토큰 처리 코드를 되살려야 한다
D. 자동 업데이트를 접는다 새 버전이 있다는 것만 알리고 받는 것은 사람이 한다. 그러려면 확인 호출도 익명으로 되어야 해서 결국 A 나 B 가 필요하다
추천은 B 다. 소스 공개 여부를 지금 정하지 않아도 되고, 앱 코드에서 바뀌는 것은 저장소 이름 하나다. 공증받은 DMG 는 그 자체로 서명이 검증되니 릴리즈 파일이 공개된 곳에 있어도 안전 문제는 새로 생기지 않는다.
이 갈림길은 닫혔다. A 로 정했다. doortts/clf 를 공개로 돌려 배포처로 쓰고, 이슈와 소스 원본은 사내 GHE 에 둔다. 두 저장소의 역할과 링크 지도는 17-repo-split.html 이 정한다.

2. 어떤 도구로 만드나

업데이트 프레임워크를 안 쓴다. macOS 에서 이 자리의 표준은 Sparkle 인데, Sparkle 이 대신 해 주는 어려운 일 둘을 우리는 이미 다른 방법으로 풀었다.

Sparkle 이 해 주는 것우리가 이미 가진 것
appcast XML 로 새 버전 알리기 GitHub Releases API 한 번 호출. 별도 서버도 XML 도 없다
EdDSA 서명으로 내려받은 것 검증 애플 공증. spctl -a 가 검사한다. 우리가 키를 만들고 보관하고 돌릴 일이 없다
업데이트 UI 창 팝오버 설정 안 한 칸. Sparkle 의 창은 LSUIElement 메뉴바 앱과 결이 안 맞는다
번들 교체와 재실행 이것만 우리가 만든다. bash helper 20 줄

남는 것이 네 번째 하나라서 의존성을 하나 들이는 대신 직접 만든다. 이 저장소는 핵심 타겟에 의존성 0 을 지키는 곳이고 Xcode 프로젝트도 없다. Sparkle 을 넣으면 그 두 가지가 같이 흔들린다.

쓰는 도구어디서무엇에
URLSession앱 안릴리즈 조회와 DMG 내려받기. 진행률과 무활동 타임아웃
hdiutil앱 안DMG 를 명시한 지점에 붙였다가 곧바로 뗀다
ditto앱 안 / helper서명과 확장 속성을 지키며 복사
spctl -a -vv앱 안관문. 공증 티켓을 확인한다
bash helper앱 밖부모가 죽기를 기다렸다가 제자리 교체하고 다시 띄운다
codesign, notarytool, stapler릴리즈 기계서명, 공증, 티켓 붙이기
gh릴리즈 기계태그와 릴리즈 생성, DMG 올리기

3. 전체 과정

만드는 쪽 내 기계에서 scripts/release.sh v0.1.0 --publish 한 번
1
태그를 붙인다
git tag -a v0.1.0
버전 문자열이 여기서 나온다. 태그가 없으면 커밋 해시가 박혀 비교할 수 없다
->
2
짓고 서명한다
swift build + codesign
Developer ID, hardened runtime, 보안 타임스탬프. 인증서는 키체인에서 찾는다
->
3 관문
서명을 먼저 본다
codesign --verify --deep --strict
공증 왕복은 몇 분이다. 여기서 걸릴 것을 거기까지 들고 가지 않는다
->
4
앱을 공증한다
zip 으로 싸서 애플에 올리고 status: Accepted 를 확인한다. 이 zip 은 올리는 용도라 릴리즈에 안 붙는다
->
5
티켓을 앱에 박는다
stapler staple
DMG 를 만들기 전에 한다. 그래야 꺼낸 앱에 티켓이 따라온다
6
DMG 로 싼다
hdiutil create
스테이플된 앱을 ditto 로 옮겨 담는다. /Applications 링크는 안 넣는다. clf 는 ~/Applications 에 산다
->
7
DMG 도 공증한다
브라우저로 직접 받아 여는 사람이 이 티켓을 본다. 공증이 두 번인 이유가 이것이다
->
8 관문
내 자산을 스스로 평가
spctl -a -vv 가 Notarized Developer ID 라고 답해야 한다. 사용자 기계가 할 검사와 같은 것이다. 여기서 안 되는 걸 올리면 거기서도 막힌다
->
9 되돌릴 수 없음
내보낸다
태그 push, gh release create --repo ...
여기까지가 --publish 를 줬을 때만 도는 구간이다

1 - 8 은 몇 번을 돌려도 안전하다. 그래서 기본값이고, 되돌릴 수 없는 9 만 --publish 뒤에 둔다. 포장만 시험할 때는 --skip-notarize 로 공증을 건너뛰어 몇 초에 끝낸다.

v
릴리즈 저장소 두 기계가 만나는 유일한 곳
주소 (정해야 한다)
github.com/doortts/clf - 지금은 비공개
태그
v0.1.0
자산 하나
clf-v0.1.0.dmg
릴리즈 노트
--generate-notes

앱이 보는 것은 GET /repos/<소유자>/<저장소>/releases/latest 하나다. 응답의 tag_name 으로 버전을 비교하고 assets 에서 .dmg 로 끝나는 것을 고른다. 이 호출이 익명으로 되느냐가 1절의 갈림길이다.

v
쓰는 쪽 사용자 기계. 앱이 스스로 한다
1
확인한다
켤 때 한 번, 그 뒤 24시간마다. ETag 를 보내 304 를 받으면 한도를 안 깎는다
->
2
버전을 견준다
semver 비교. 자기 버전이 태그 꼴이 아니면 개발 빌드로 보고 아무것도 안 한다
->
3
점을 올린다
팝오버 톱니에 점 하나. 숫자도 글자도 없다. 사용자가 설정을 열 이유를 만드는 것이 전부다
->
4
사람이 누른다
설치하고 다시 시작. 여기까지 자동으로 오지 않는다. 앱을 갈아 끼우는 일은 사람이 시작한다
->
5
받는다
캐시 폴더로 내려받는다. 30초 동안 새 조각이 안 오면 멈춘 것으로 보고 끊는다
6
붙였다 뗀다
hdiutil attach 로 우리가 정한 지점에 붙이고, .app 을 꺼낸 뒤 곧바로 detach. 안 떼면 Finder 에 볼륨이 쌓인다
->
7 관문
공증을 확인한다
spctl -a -vv 가 Notarized Developer ID 가 아니면 여기서 멈춘다. helper 에게 번들을 덮어쓸 권한을 주기 전 마지막 검사다
->
8
helper 를 띄우고 죽는다
자기를 지우면서 자기를 복사할 수 없다. 밖에서 기다릴 손을 detached 로 띄우고 NSApp.terminate. 로그 경로를 먼저 남긴다
->
9
제자리에서 바꾼다
부모가 죽기를 기다린 뒤 mv 두 번. 번들이 없는 순간이 없다. 경로가 그대로라 로그인 항목 등록도 안 끊긴다
->
10
다시 뜬다
open. 새 버전이 메뉴바에 돌아온다. 성공하면 캐시를 지우고, 실패하면 남긴다

실패하면 두 개가 남는다. 받아 둔 DMG 와 ~/Library/Logs/clf/update-<tag>.log. 앞의 것은 사람이 직접 설치할 수 있는 가장 짧은 길이고, 뒤의 것은 helper 가 앱이 죽은 뒤에 돌기 때문에 남는 유일한 단서다.

4. 지금 어디까지 왔나

단계상태무엇이
만드는 쪽 2 - 5확인함 Developer ID 서명, 앱 공증(Accepted), 스테이플, spctl 이 Notarized Developer ID. 격리 딱지를 강제로 붙인 사본도 통과해서 xattr 을 버린 판단이 맞았다
만드는 쪽 1, 6 - 9막힘 notarytool 키체인 프로필이 사라져 다시 등록해야 한다. 그리고 릴리즈 저장소를 정해야 한다 (1절)
스크립트 손질할 것 --publish 분리, --skip-notarize, --repo 명시, 인증서 자동 탐색
쓰는 쪽 1 - 2할 것 UpdateCheck.swift. 순수 함수라 릴리즈가 없어도 테스트로 잠근다. 지금 바로 시작할 수 있는 유일한 칸이다
쓰는 쪽 3 - 10할 것 화면, 내려받기, 마운트, 관문, helper
순서. 릴리즈 저장소를 정하는 것이 먼저다. 그게 정해져야 확인 호출에 토큰이 필요한지가 정해지고, 그 답이 UpdateCheck.swift 의 모양을 바꾼다. 저장소만 정해지면 notarytool 프로필 등록과 나머지는 순서대로 흐른다.
