# 03. 요청 흐름과 실패 모드

요청 하나의 전 생애, 앱 시작/종료 시퀀스, 실패 모드별 설계된 대응.

---

## 1. 요청 하나의 흐름

```
클라이언트 요청 도착
   |
   v
[1] body 전량 버퍼링 (<= maxRetryBodyBytes, 기본 8 MiB)
   |    초과하면 swappable = false. 스왑 없이 그대로 통과시킨다
   v
[2] body JSON 에서 model 추출, 헤더에서 X-Claude-Session-Id 추출
   |
   v
[3] isConversationStart 판정 (세션 id 첫 관측 여부)
   |
   v
[4] 스왑 루프 시작. tried = {}
   |
   +---> [4a] Router.select(model:tried:isConversationStart:)
   |            |
   |            +-- .exhausted(unblockable:) ------------> [7] 종단
   |            +-- .wait(until) --+
   |            |                  |  grace 예산 내인가
   |            |                  +-- yes -> 대기 후 [4a] 재시도
   |            |                  +-- no  -> [7] 종단
   |            +-- .selected(sel)
   |                   |
   |            [4b] 헤더 변환
   |                   strip -> rewriteAuth(token) -> injectAnthropicVersion
   |                   [포팅 01] 순서 고정
   |                   |
   |            [4c] URL 조립 (문자열 결합. URLComponents 금지)
   |                   |
   |            [4d] 업스트림 실행
   |                   |
   |            [4e] content-type 으로 형태 결정
   |                   text/event-stream -> streaming, 그 외 -> buffered
   |                   |
   |            [4f] streaming 이면 첫 프레임 peek  [포팅 03]
   |                   |
   |            [4g] classifyResponse  [포팅 02]
   |                   |
   |                   +-- nil (통과) --------------------> [5]
   |                   |
   |                   +-- 트리거 있음
   |                          |
   |                          +-- streaming 이었으면 나머지를 상한까지
   |                          |   드레인해서 buffered 로 강등 (재생용)
   |                          |
   |                          +-- Router.apply(outcome:)
   |                          +-- tried.insert(sel.accountID)
   |                          +-- audit 기록
   |                          |
   +--------------------------+ 루프. 최대 priority.count 회
   |
   v
[5] 통과 경로 - 클라이언트에 쓴다 (여기서 처음으로 바이트가 나간다)
   |
   +-- buffered  : writeHead + end(body)
   +-- streaming : writeHead + firstFrame + tail + 릴레이 펌프
   |                릴레이 중에는 재분류하지 않는다
   v
[6] usage 기록, rateLimit 스냅샷 갱신, 활성 계정 갱신
   |
   v
[7] 종단 (풀 소진): 마지막 실패 응답을 원문 그대로 재생
       세션당 poolExhausted 사건 1건만 기록
       unblockable 이 비어있지 않으면 배너에 "무엇을 켜면 풀리는지" 를 싣는다
```

### 불변식

- **[5] 이전에는 클라이언트 소켓에 한 바이트도 쓰지 않는다.** 이 한 줄이 peek 설계 전체를
  강제한다
- **writeHead 는 응답당 정확히 한 번.** 재진입은 no-op
- **[5] 이후에는 재분류하지 않는다.** 릴레이 중 `event: error` 가 와도 원문 전달
- Router actor 는 [4d] 동안 잠기지 않는다. [4a] 에서 스냅샷을 받고 [4g] 후에 적용한다

## 2. 시작 시퀀스

```
앱 실행
  |
  +-- [1] accounts.json / runtime.json 로드
  |        실패해도 치명적이지 않다. 빈 상태로 진행하고 진단 로그에 남긴다
  |
  +-- [2] Keychain 접근 확인 (계정별 토큰 존재 여부만. 값은 필요할 때 조회)
  |
  +-- [3] 포트 바인딩
  |        +-- 성공        -> [4]
  |        +-- 사용 중     -> 우리 이전 인스턴스인가
  |                            +-- 맞음 -> 기존 앱 전면으로, 이 인스턴스 종료
  |                            +-- 아님 -> 다음 빈 포트 폴백
  |
  +-- [4] settings.json 검사
  |        +-- 우리 값 있고 포트 일치   -> 그대로
  |        +-- 우리 값 있고 포트 불일치 -> 갱신 (이전 실행의 stale 값 복구)
  |        +-- 우리 값 없음             -> 사용자가 활성화한 상태면 주입
  |        +-- 다른 값 있음             -> 덮어쓰지 않고 배너로 알린다
  |
  +-- [5] 만료된 쿨다운 정리 (7일 지난 modelCooldowns 항목 제거)
  |
  +-- [6] 메뉴바 아이템 표시. 준비 완료
```

주입은 **[3] 이 성공한 뒤에만** 한다. 포트가 안 잡혔는데 settings.json 을 먼저 쓰면
Claude Code 가 죽은 포트를 향해 요청을 보낸다.

## 3. 종료 시퀀스

```
사용자가 종료 선택 (또는 SIGTERM)
  |
  +-- [1] 새 요청 수락 중단
  +-- [2] settings.json 에서 우리 키 제거     <- 계약의 핵심
  +-- [3] 진행 중인 요청에 유예 시간 부여 (수 초)
  +-- [4] runtime.json 최종 플러시
  +-- [5] 종료
```

**[2] 가 계약이다.** 사용자가 앱을 끄면 Claude Code 가 고장 나는 것이 아니라 그냥
원래대로 직접 호출로 돌아가야 한다. 이걸 빠뜨리면 "clfl 을 껐더니 Claude Code 가
안 된다"는 최악의 실패 모드가 된다.

크래시로 [2] 를 못 하는 경우는 다음 실행의 시작 [4] 가 복구한다. 그 사이 사용자는
연결 거부를 겪는데, 이걸 줄이려면 로그인 항목 등록을 권장한다.

## 4. 실패 모드

설계된 대응을 미리 못박는다. 표에 없는 것은 설계 누락이다.

### 인프라

| 상황 | 감지 | 대응 | 사용자에게 |
|---|---|---|---|
| 포트 바인딩 실패 | 시작 [3] | 다음 빈 포트 폴백 + settings.json 갱신 | 조용히. 반복되면 알림 |
| settings.json 에 남의 값 | 시작 [4], 주기 검사 | 덮어쓰지 않음 | 배너 + 강제 적용 버튼 |
| settings.json 에서 우리 값 사라짐 | 주기 검사 | 재주입 제안 | `proxyDetached` 조건 |
| settings.json 파싱 실패 | 읽기 | 쓰지 않음. 백업 유지 | 배너 + 파일 열기 버튼 |
| Keychain 접근 거부 | 토큰 조회 | 그 계정만 스킵 | 계정 카드에 오류 표시 |
| runtime.json 손상 | 로드 | 빈 상태로 시작 | 진단 로그만 |
| 디스크 가득 (JSONL append 실패) | 쓰기 | **로깅만 중단. 라우팅은 계속** | 배너 |

**로깅 실패가 요청 경로를 막으면 안 된다.** claulay 의 자세를 그대로 가져간다.
모든 부가 I/O 는 best-effort 이고 요청 처리에 예외를 던지지 않는다.

### 라우팅

| 상황 | 감지 | 대응 | 사용자에게 |
|---|---|---|---|
| 401 | 분류 | 계정 `invalid`. 시간으로 회복 안 됨 | 계정 카드 `!` + 재로그인 버튼 |
| 429 session_limit | 분류 | 계정 전체 쿨다운 | 카드에 남은 시간 |
| 429 rate_limit | 분류 | (계정, 모델) 쿨다운 | 카드에 모델별 표시 |
| 일시 과부하 429 연쇄 | transient 판정 | 5초 쿨다운 + grace 대기 후 재훑기 | 조용히 |
| 전 계정 진짜 소진 | 선택 `.exhausted` | 마지막 실패 응답 원문 재생 | `poolExhausted` 조건 + 알림 |
| 소진됐으나 제외해 둔 계정에 여유 있음 | `.exhausted(unblockable:)` | **끌어다 쓰지 않는다.** 뺀 이유를 배신하지 않기 위함 | 배너에 "무엇을 켜면 풀리는지" 와 켜기 버튼 |
| 자동 전환 대상 0개 | 선택 진입 시 | 모든 요청 실패 | `autoSwitchAllDisabled` 조건 + 알림 |
| cross-plan 스왑 | 선택 결과 | 그대로 진행 (warn and allow) | `crossPlanActive` 조건 배너 |
| 선제 전환 직후 또 전환 조건 성립 | 쿨다운 300초 | 선제 강등만 건너뛴다. **반응형은 막지 않는다** | 없음 |
| 묵은 잔여 스냅샷 | `resetsAt` 이 지남 | 그 창 읽기를 버린다. 둘 다 없으면 tier 1 | 없음 |
| body 8 MiB 초과 | 버퍼링 [1] | 스왑 불가. 그대로 통과 | 타임라인 기록 |
| 요청 body 에 model 없음 | 파싱 [2] | 모델 쿨다운 스코프를 계정 전체로 승격 | 없음 |

### 스트리밍

| 상황 | 감지 | 대응 |
|---|---|---|
| 업스트림이 경계 없이 종료 | peek `closedEmpty` | 받은 바이트를 그대로 쓰고 종료 |
| 업스트림 중간 끊김 | 릴레이 catch | **`end()` 하지 말고 소켓 강제 종료** |
| 클라이언트 중단 | Task 취소 | 업스트림 즉시 abort. usage 미기록 |
| 릴레이 중 `event: error` | - | 재분류 없이 원문 전달 |

중간 끊김에서 `end()` 를 부르면 chunked 종단자가 나가 잘린 스트림이 완결된 것처럼
보인다. Claude Code 에서 "Response stalled mid-stream" 으로 나타나던 증상이다.
자세한 것은 [포팅 03](../porting/03-sse-streaming.md) 7절.

## 5. 진단 (doctor)

메뉴바에서 한 번에 돌리는 자가 점검. 각 항목은 통과 여부와 조치 힌트를 낸다.

| 항목 | 검사 | 실패 시 조치 |
|---|---|---|
| 포트 | 우리가 바인딩하고 있는가 | 재시작 |
| settings.json | 우리 값이 현재 포트를 가리키는가 | 재주입 버튼 |
| 도구 검색 | `ENABLE_TOOL_SEARCH` 가 켜져 있는가 | 켜기 버튼. 기본값은 켬 |
| 백업 | `settings.json.clfl.bak` 존재 | 정보성 |
| Keychain | 계정 수만큼 토큰이 있는가 | 누락 계정에 재등록 버튼 |
| 계정 | 우선순위 체인이 비어있지 않은가 | 설정 열기 |
| 유효 계정 | invalid 가 아닌 계정이 1개 이상 | 재로그인 안내 |
| 자동 전환 대상 | `autoSwitch` 가 켜진 계정이 1개 이상 | 계정 목록 열기 |
| 토큰 만료 | 남은 기간이 30일을 넘는가 | 계정별 재등록 버튼 |
| 저장소 | Application Support 쓰기 가능 | 권한 안내 |
| 로그인 항목 | 등록되어 있는가 | 정보성. 등록 버튼 |

claulay 의 `doctor` 와 목적은 같지만 항목이 다르다. vault, daemon, claude 바이너리
검사가 빠지고 settings.json 소유권 검사가 들어온다.

## 6. 성능 관점

메뉴바 앱이므로 처리량이 아니라 **상주 비용**이 제약이다.

| 항목 | 목표 | 근거 |
|---|---|---|
| 유휴 시 CPU | 거의 0 | 이벤트 기반. 폴링 루프를 두지 않는다 |
| 유휴 시 메모리 | 수십 MB | 사용자 한 명의 대화. 커넥션 풀은 작게 |
| 요청 추가 지연 | 1 ms 미만 | 로컬 홉 하나. peek 는 첫 프레임까지만 |
| runtime.json 쓰기 | 1초 debounce | 요청마다 쓰지 않는다 |
| ratelimit 갱신 | 응답 헤더 편승 | 별도 폴링 API 호출 없음 |

**폴링을 만들지 않는다.** 5h/7d 잔여는 어차피 응답 헤더로 들어오므로 요청이 흐르면
저절로 갱신된다. 요청이 없으면 갱신할 이유도 없다.

## 7. 구현 순서

세로로 얇게 관통하는 순서로 쌓는다. 각 단계가 끝나면 실제로 동작하는 것이 있어야 한다.

| 단계 | 산출물 | 검증 |
|---|---|---|
| 1 | ClflCore: 헤더 변환 + 분류 + reset epoch | claulay 테스트 케이스 이식본 통과 |
| 2 | ClflCore: SSE 경계 스캐너 + 파서 | 같음 |
| 3 | ClflCore: 선택 알고리즘 + 쿨다운 산술 | 가짜 시계로 결정적 테스트 |
| 4 | ClflStore: Keychain + accounts.json + runtime.json | 단위 테스트 |
| 5 | ClflProxy: 단일 계정 통과 프록시 (스왑 없음) | 실제 Claude Code 로 대화 성공 |
| 6 | ClflProxy: 스왑 루프 + 릴레이 펌프 | 가짜 executor 로 429 시퀀스 |
| 7 | ClflStore: settings.json 관리 + 시작/종료 시퀀스 | 켜고 끄고 크래시 복구 |
| 8 | ClflApp: 메뉴바 + 계정 목록 + 게이지 | 손으로 확인 |
| 9 | ClflApp: 계정 CRUD + 우선순위 드래그 | 손으로 확인 |
| 10 | 조건/사건 표시, 알림, doctor | 손으로 확인 |
| 11 | 선제 전환 임계값 | usage/audit 조인으로 임계값 실측 |

5단계가 첫 관문이다. **스왑 없이 그냥 통과만 시키는 프록시로 Claude Code 데스크톱 앱이
정상 동작하는지**를 먼저 확인해야 한다. 여기서 [README](../../README.md) 에 적은
MCP tool search 와 Remote Control 제약이 실제로 어떻게 나타나는지도 드러난다.

11단계를 마지막에 둔 이유는 임계값을 추측으로 정할 수 없기 때문이다. 1단계부터 쌓인
`usage.jsonl` 과 `audit.jsonl` 이 있어야 스왑당 캐시 재생성 비용을 계산할 수 있다.
