빨강 구간이 벽지 위에서 눈을 아프게 하는 이유

스크린샷의 상태(사용률 96%, 빨강 구간)를 실제 색값으로 재현해서 벽지 여덟 벌 위에 얹었다. 결론부터: 빨강만 팔레트의 밝기 사다리에 구멍이 나 있다. 나머지 셋은 L* 78 에서 92 사이인데 빨강 혼자 58 이라, 중간 밝기 벽지에서 대비가 1.1 에서 1.5 까지 떨어지면서 채도 차이만 남는다. 그 조합이 눈이 아픈 진짜 원인이다.

1. 지금 색이 어디서 오나

메뉴바 막대는 ImageRenderer 로 구운 이미지다. 템플릿을 꺼서 색을 살리는 대신 색이 구울 때 박힌다. 그래서 적응형 색을 못 쓰고, BarImage.menuBarIsDark 가 지금 메뉴바가 어두운지 밝은지를 보고 두 팔레트 중 하나를 고른다.

2. 벽지 위에서 실제로 이렇게 보인다

아래는 소스의 치수(코드 12pt, 숫자 10pt, 눈금 20칸)와 색값을 그대로 옮긴 재현이다. 왼쪽이 실제 크기, 오른쪽은 3배 확대다. 스크린샷의 상태를 그대로 넣었다: T52, 5시간 창 96% 빨강, 주간 창 68% 초록.

3. 숫자로 본 원인

같은 재현을 대비비로 옮긴 표다. 글자는 10pt 얇은 획이라 WCAG 기준으로는 4.5:1, 최소한 3:1 은 필요하다.

회색은 3:1 미만, 빨간 칸은 2:1 미만이다. 대비가 2 아래면 밝기로는 사실상 같은 색이고, 눈은 색상 차이만으로 글자 경계를 찾아야 한다.

왜 아픈가. 원인이 둘 겹쳤다.
  • 밝기 대비가 사라지고 채도 차이만 남는다. 중간 남색 벽지에서 빨강 글자의 대비는 1.53:1 인데 채도 차이는 49 다. 밝기 경계가 없으면 눈은 초점을 맺을 자리를 못 찾고 계속 조절근을 움직인다. 글자가 떨리는 것처럼 보이는 감각이 이것이다.
  • 채도 높은 빨강과 파랑은 눈 안에서 초점 거리가 다르다. 파장이 긴 빨강이 앞에, 짧은 파랑이 뒤에 맺힌다(색수차). 두 색의 밝기가 비슷할 때 이 차이가 가장 크게 느껴져서 빨강 글자가 벽지에서 떠오르는 것처럼 보인다. 채도를 낮추면 그만큼 줄어든다.
스크린샷의 벽지는 정확히 이 두 조건을 동시에 만족하는 중간 채도 남색이다.

구조적 원인 하나 더: 팔레트는 둘, 벽지는 연속이다

menuBarIsDark 는 참과 거짓 둘로 답한다. 그런데 메뉴바 바탕은 벽지가 그대로 비쳐서 L* 3 부터 96 까지 연속이다. 다크 팔레트의 값은 L* 10 근처를 겨냥해 고른 것이라 L* 40 에서 60 사이 벽지에서는 어느 색이든 대비가 무너진다. 빨강이 가장 심하게 무너지는 것일 뿐이고, 중간 밝기 벽지에서는 무채색 글자조차 3:1 을 못 넘긴다(청록 벽지에서 2.42).

이 기계에서 방금 메뉴바를 캡처해 재 봤다. 지금은 밝은 벽지라 L* 95 이고 라이트 팔레트가 걸린다. 그쪽에서도 빨강 #e02017 은 흰 메뉴바에서 4.39:1 로 10pt 글자 기준을 겨우 못 넘긴다.

4. 제안

A안: 글자색과 눈금색을 가른다 (권장)

고칠 곳이 한 함수다. 지금 barTextColor 는 dotColor 를 그대로 돌려준다. 이 둘을 가르면 각자에게 맞는 값을 줄 수 있다. 

// 지금
func barTextColor(dark: Bool) -> Color { dotColor(dark: dark) }

// 제안: 글자는 밝기를 벌고 채도를 버린다. 눈금은 그대로 둔다
func barTextColor(dark: Bool) -> Color {
    switch self {
    case .empty: return dark ? Color(hex: 0xffab9e) : Color(hex: 0x9e1b12)
    case .low:   return dark ? Color(hex: 0xffe98c) : Color(hex: 0xbf7f00)
    default:     return dotColor(dark: dark)
    }
}

무채색 상한 #e5e5ea913 15.765.694.073.18
  • 대비가 어두운 벽지에서 두 배 가까이(5.93 -> 10.90), 중간 벽지에서 1.53 -> 2.82 로 오른다. 채도는 82 -> 35 로 절반 아래라 색수차도 같이 준다
  • 빨강이 세 곳에서 동시에 칠해지는 것도 준다. 지금은 숫자, 눈금 테두리, 눈금 채움이 모두 같은 채도의 빨강이다. 글자만 연하게 빼면 빨강 면적이 줄어 오래 봐도 덜 피곤하다
  • 연한 산호가 위험으로 덜 읽힌다는 반론이 있다. 그런데 빨강 구간은 눈금이 이미 꽉 차 있다. 위험 신호는 색이 아니라 그 채움이 낸다. 색은 거들 뿐이다
  • 노랑도 같이 손댄다. #ffe500 은 채도 90 짜리 원색 노랑이라 글자로는 과하다. #ffe98c 는 밝기를 지키면서 채도만 절반이다

세 안을 나란히

대비가 가장 나빴던 바탕 셋에 세 안을 얹었다. 전부 2배 확대다.

B안: 막대 뒤에 판을 깐다

A안은 글자를 고치지만 눈금은 여전히 벽지에 묻는다. 중간 밝기 벽지에서 눈금이 뭉개지는 것까지 고치려면 바탕을 우리가 정해야 한다. 막대 전체 뒤에 검정 42% 판을 두면 벽지가 무엇이든 대비가 고정된다.

  • 모든 구간이 한 번에 나아진다. 팔레트를 손대지 않아도 다크 값이 겨냥한 L* 10 근처 바탕이 항상 만들어진다
  • 대신 메뉴바 다른 항목들과 결이 달라진다. 시스템 항목은 바탕 없이 산다
  • A안과 겹쳐 쓸 수 있다. 판을 깔면 연한 산호도 대비 9 이상이 나온다

C안: 팔레트를 셋으로 늘린다

근본 원인(팔레트 둘, 벽지 연속)을 직접 고치는 길이다. 벽지 밝기를 재서 어두움/중간/밝음 세 벌 중 하나를 고른다. 다만 메뉴바 아래 벽지 픽셀을 읽는 경로가 지금 없고, 벽지가 바뀔 때마다 다시 구워야 한다. 얻는 것보다 드는 것이 크다. A안과 B안이 같은 증상을 훨씬 싸게 덮으므로 지금은 접는다.

추천. A안을 먼저 넣는다. 값 셋을 바꾸는 일이고 되돌리기도 쉽다. 그걸로도 눈금이 벽지에 묻는 것이 거슬리면 B안을 겹친다. 판의 불투명도는 설정에 노브로 내놓지 않는다. 노브가 늘면 조합마다 대비를 다시 봐야 한다.
