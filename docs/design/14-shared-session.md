# 14 세션 공유

[13 문서](13-multi-instance.md)에서 계정마다 창을 따로 띄웠고, 그 창들 사이로 대화를
옮기는 이전 기능을 만들었다. 쓰다 보니 옮기는 것 자체가 일이다. 한도가 바닥나서
다른 계정으로 갔다가, 리셋되면 도로 옮겨 온다. 한 대화를 사흘 붙들고 있으면 이
왕복이 하루에 몇 번씩 생긴다.

**옮기지 말고 양쪽에 두면 안 되나.** 이 문서는 그 질문의 답과 설계다.

## 왜 되나

세션 레코드에는 계정 정보가 **파일 안에 없다.** 계정은 폴더 경로다.

```
claude-code-sessions/<사람>/<계정 uuid>/local_<sessionId>.json
```

레코드가 가리키는 대화 본문은 계정 폴더 바깥에 하나뿐이다.

```
~/.claude/projects/<프로젝트>/<cliSessionId>.jsonl
```

즉 **대화는 이미 공유돼 있다.** 계정별로 갈라진 것은 그 대화를 목록에 띄우는
포인터뿐이고, 이전 기능(`SessionHandoff.move`)이 하는 일은 포인터를 옮기는 것이다.
구현도 복사한 뒤 원본을 지우는 순서다. 지우지 않으면 그것이 공유다.

청구도 그대로다. 어느 계정 창에서 이어가느냐가 결제를 정하지 레코드 위치가 정하지
않는다. 이전 기능이 성립하는 이유와 같다.

실측으로 확인한 것 하나. 한쪽 창에서 이어간 내용이 시간이 지나면 다른 창에도
나타난다. 두 창이 같은 파일을 보고 있다는 뜻이다.

## 무엇이 문제인가

### 레코드 상태가 갈라진다

레코드에는 대화 본문 말고도 창별 상태가 들어 있다.

```
lastActivityAt  lastFocusedAt  completedTurns  title  titleSource
model  effort  permissionMode  writtenBranches  isArchived
```

두 계정이 각자 사본을 갱신하므로 목록의 제목과 턴 수와 마지막 시각이 갈라진다.
손상은 아니지만 **옛 사본에서 열면 그때 저장된 `model`, `effort`, `permissionMode`
로 재개된다.** 어제 xhigh 로 돌리던 대화를 옆 계정에서 열었더니 medium 이더라는
일이 생긴다.

### 겹침 경고가 거짓말이 된다

[13 문서](13-multi-instance.md) 12절의 경고는 "서로 다른 계정 창 둘이 한 대화에
같이 쓰는 중" 을 잡는다. 공유가 정상 동작이 되면 그 조건이 늘 참이다.

그런데 **경고를 끄면 안 된다.** 공유의 전제가 "동시에 쓰지 않는다" 이므로, 동시에
쓰는 순간이 바로 사용자가 알아야 할 사고다. 끄는 것이 아니라 말을 바꿔야 한다.

### 상태를 맞추면 경고가 저절로 켜진다

이 설계에서 가장 조심할 자리다. 갈라진 레코드를 맞추려고 최신본을 반대쪽에
복사하면 그 사본의 `lastActivityAt` 도 같이 넘어간다. 그러면 손도 안 댄 계정이
"방금 썼다" 로 보이고, 방금 고친 겹침 규칙(두 계정 다 15분 안)이 그 가짜 활동에
걸린다. **동기화가 경고를 만든다.**

## 설계

### 한 줄 요약

공유 목록을 clf 가 들고, 그 목록에 있는 대화만 **최신 레코드를 반대쪽에 덮어쓴다.**
덮어쓸 때 무엇을 썼는지 기억해 두고, 겹침 판정은 그 기억과 다른 값만 진짜 활동으로
센다.

### 새 조각

| 이름 | 자리 | 하는 일 |
|---|---|---|
| `SharedSessions` | ClfDesktop | 공유 목록 파일. 어느 대화를 어느 계정들이 공유하는지, 그리고 우리가 마지막으로 덮어쓴 값 |
| `SessionHandoff.share` | ClfDesktop | `move` 에서 삭제만 뺀 것 |
| `SharedSync` | ClfDesktop | 공유 대화의 레코드를 최신본으로 맞춘다. 창이 떠 있는 계정에만 |
| `SessionDuplicate.live` 의 `ownWork` | ClfDesktop | 덮어쓴 값과 같은 활동은 안 센다 |

### 공유 목록

`~/Library/Application Support/clf/shared-sessions.json`. `HandoffGrace` 와 같은
자리, 같은 방식이다.

```
{
  "cb99a8ae-...": {
    "accounts": ["2a063dae-...", "746e81ae-..."],
    "sharedAt": 1786288336445,
    "mirrored": { "746e81ae-...": 1786288336445 }
  }
}
```

- `accounts` 는 이 대화를 공유하는 계정. 둘 이상이다
- `mirrored` 는 **우리가 그 계정에 써 넣은 `lastActivityAt`**. 겹침 판정이 이 값을
  본다

디스크만 보고 공유를 알아낼 수도 있다(레코드가 두 폴더에 있으면 공유). 그렇게 하지
않는 이유는 **의도를 구별할 수 없기** 때문이다. 이전하다 만 찌꺼기와 일부러 공유한
것이 디스크에서는 같은 모양이다. 경고를 켤지 말지가 그 구별에 달렸으므로 의도를
따로 적는다.

### 공유 만들기

지금 이전 창의 단추 옆에 하나 더 둔다.

```
[ 옮기기 ]  [ 양쪽에 두기 ]
```

`SessionHandoff.move` 의 마지막 삭제 루프만 건너뛰면 복사가 된다. 두 동작이 앞부분을
공유하도록 `place(_:into:)` 를 뽑아낸다.

```swift
public static func share(_ fileName: String,
                         from source: [SessionStore], to target: [SessionStore]) throws {
    try place(fileName, from: source, into: target)   // move 와 같은 몸통
    // 지우지 않는다. 그것이 전부다
}
```

공유가 성립하면 `SharedSessions` 에 적는다. 실패하면 아무것도 안 적는다. 목록에만
있고 디스크에 없는 상태가 제일 나쁘다.

### 상태 맞추기

레코드는 턴마다 바뀌는데 그 변화가 뜻을 가지는 순간은 계정을 바꿀 때뿐이다. 한
계정으로 종일 일하는 동안 반대쪽 폴더를 계속 고쳐 봐야 볼 사람이 없다. 그래서
파일 변경을 좇지 않고 **볼 사람이 생기는 순간**에 맞춘다.

| 계기 | 하는 일 |
|---|---|
| clf 가 그 계정 창을 띄우기 직전 | 띄우기 전에 폴더를 맞춘다. 앱은 시작할 때 목록을 읽는다 |
| 5초 감시 루프 | 바닥. 위가 놓친 것을 늦어도 5초 안에 잡는다 |

띄우기 직전이 제일 중요하다. clf 가 순서를 쥐고 있어 우리 쓰기와 앱의 읽기가 겹칠
일이 없다. 5초 루프는 `mirrorBackAll()` 이 이미 도는 자리라 주기를 새로 만들지
않는다.

한 대화에 대해:

1. 공유 계정들의 레코드를 읽는다
2. `lastActivityAt` 이 가장 큰 것이 최신본이다
3. **창이 떠 있는 계정에만** 덮는다. 창이 없으면 그 목록을 읽을 프로세스가 없다
4. 대상이 더 최신이거나 같으면 건너뛴다
5. 덮은 계정마다 `mirrored[계정] = 그 lastActivityAt` 을 적는다

3번과 4번이 쓰기 폭풍을 막는 자리다. 3번이 없으면 A 로 일하는 내내 턴마다 B 폴더에
쓴다. 4번이 없으면 우리가 쓴 것을 다음 바퀴에 다시 최신으로 보고 되받아 쓴다.

늦은 쪽이 지는 규칙이다. 사용자가 동시에 안 쓴다는 전제에서는 진 쪽이 잃는 것이
UI 상태뿐이고, 대화 본문은 애초에 공유 파일이라 손대지 않는다.

레코드는 420바이트다. `stat` 으로 먼저 걸러 파싱을 아끼는 것도 생각했지만 읽기가
이미 그만큼 싸서 안 넣는다. 비용을 정하는 것은 읽기가 아니라 쓰기이고, 쓰기는 3번과
4번이 막는다.

### 왜 파일 감시가 아닌가

FSEvents 로 레코드 변경을 받으면 5초를 안 기다려도 된다. 그런데 이 그림에서는 진다.

- 변경은 턴마다 오는데 뜻이 있는 순간은 하루 몇 번이다. 받은 것 대부분을 3번과 4번
  게이트에서 버린다
- 이벤트를 받아도 게이트는 그대로 필요하다. 우리가 쓴 것이 다시 이벤트로 돌아온다
- 커널 버퍼가 넘치면 `MustScanSubDirs` 만 오고 무엇이 바뀌었는지는 안 온다. clf 가
  꺼져 있던 동안의 변경도 안 온다. 결국 바닥 스캔은 남는다

트리거를 바꿔도 `SharedSync.run()` 은 안 바뀌게 짠다. 나중에 5초가 거슬리면 그때
얹는다.

파일 이름이 계정마다 다를 수 있다(`local_<sessionId>.json` 의 sessionId 는 레코드
고유값이다). 공유 목록의 열쇠는 `cliSessionId` 이므로, 계정 폴더에서 그 cli 를
가리키는 레코드를 찾아 이름은 대상 쪽 것을 유지한 채 내용만 덮는다. 이름을 같이
바꾸면 앱이 목록에서 그 줄을 잃는다.

### 겹침 판정 고치기

`SessionDuplicate.live` 는 지금 계정별 `lastActivityAt` 이 15분 안인 계정을 센다.
여기에 조건 하나를 더한다.

```
그 계정의 lastActivityAt 이 우리가 덮어쓴 값과 같으면 그것은 그 계정의 일이 아니다
```

`mirrored` 를 `live(...)` 에 넘겨 그 값과 일치하는 활동을 뺀다. 남은 계정이 둘
이상일 때만 경고다. 즉 **공유해 둔 대화라도 두 사람이 진짜로 15분 안에 각자
움직였을 때만** 뜬다. 그때는 문구를 바꾼다.

```
공유해 둔 대화를 두 창이 같이 쓰고 있습니다
- NAVER_TEAM_52 에서 지금 작업 중
- NAVER_TEAM_40 에서 3분 전까지 작업
한쪽에서 손을 떼세요. 기록이 섞일 수 있습니다.
```

### 공유 끊기

목록에서 지우고, 남길 계정을 고르게 한 뒤 나머지 계정의 레코드를 지운다. 즉
`share` 의 반대이고 결과는 `move` 와 같다. 이전 창에 `공유 끊기` 를 둔다.

### 지우기와 보관

한쪽에서 대화를 지우거나 보관해도 다른 쪽 레코드는 남는다. 이건 지금 이전 기능도
가진 성질이다. `syncShared` 가 `isArchived` 도 같이 덮으므로 보관은 따라간다.
삭제는 파일이 사라지는 것이라 따라가지 않는다. 공유 계정 중 하나에서 레코드가
사라지면 공유 목록에서 그 계정을 빼고, 하나만 남으면 항목을 지운다.

## 안 하는 것

| 안 하는 것 | 이유 |
|---|---|
| 동시 사용 잠금 | 앱의 파일을 우리가 잠글 수 없다. 경고가 우리가 할 수 있는 전부다 |
| 대화 본문 동기화 | 본문은 처음부터 한 파일이다. 손댈 것이 없다 |
| 자동 공유 | 대화마다 사용자가 정한다. 전부 공유하면 목록이 두 배가 되고 계정을 가른 뜻이 없어진다 |
| 레코드에 우리 필드 추가 | 앱이 자기 JSON 을 다시 쓸 때 무슨 일이 생길지 모른다. 우리 상태는 우리 파일에 둔다 |

## 단계

1. `SharedSessions` 파일과 `SessionHandoff.share`. 공유는 되지만 상태는 갈라진 채
2. `SharedSync`. 최신본 전파와 `mirrored` 기록. 창 게이트, 띄우기 직전과 5초 루프
3. 겹침 판정에 `mirrored` 반영, 문구 갈래 추가
4. `공유 끊기`

1단계만으로도 왕복은 사라진다. 2단계 없이 쓰면 목록의 제목과 턴 수가 계정마다
다르고, 옛 사본에서 열 때 모델과 권한 설정이 그때 값으로 돌아간다. 3단계 없이
2단계를 넣으면 경고가 매번 뜬다. **2와 3은 같이 가야 한다.**

## 무엇을 테스트로 잠그나

| 테스트 | 잡는 것 |
|---|---|
| `share` 는 원본을 남긴다 | 삭제를 안 건너뛰면 이전과 같아진다 |
| 최신본이 옛 사본을 덮는다 | `lastActivityAt` 비교 방향 |
| 대상이 더 최신이면 안 덮는다 | 되돌림 사고 |
| 시각이 같으면 안 덮는다 | 우리 쓰기를 되받아 쓰는 무한 왕복 |
| 창 없는 계정에는 안 쓴다 | 쓰기 폭풍 |
| 파일 이름은 대상 것을 지킨다 | 이름을 바꾸면 앱 목록에서 줄이 사라진다 |
| 덮어쓴 활동은 겹침으로 안 센다 | 동기화가 경고를 만드는 문제 |
| 둘 다 진짜로 움직이면 경고가 뜬다 | 위 규칙이 경고를 죽이면 안 된다 |
| 공유 계정이 하나 남으면 항목이 사라진다 | 목록에만 남는 유령 |
